26. Embedding Engine design

Run Otter Fusion from Otter Fusion. std:engine compiles and executes guest source inside a sandboxed isolate — its own heap, capability whitelist, host-bound modules, and hard resource limits. The substrate for embedding edge-function-style workloads, plugin systems, and trusted-but-bounded user scripts.

The substrate is real and proven: the compiler is already a Cranelift JIT (backend::compile), and the procedural-macro system (chapter 22) already compiles guest source from a string, binds host functions into a virtual core:compiler module, JIT-compiles it, and calls it by pointer at compile time. std:engine turns that one-shot, compile-time machinery into a persistent, re-entrant, sandboxed runtime surface. §10 records exactly what exists today versus what is new work.

1. The isolate model

An isolate is a self-contained execution context. It owns a private heap and garbage collector, a private set of runtime registries (channels, locks, finalizers), a frozen capability policy deciding which modules its guest code may import, a set of host bindings (native functions the guest can call), and a set of resource limits the runtime enforces. Guest code loaded into an isolate cannot observe or affect anything outside it except through the bindings and bridge values the host explicitly hands it.

This mirrors the isolate/context split familiar from V8 — but it is built on the language's own GC and Cranelift backend rather than an embedded VM, and the boundary is enforced at three layers: compile time (capability gating rejects forbidden imports before any code runs), ABI (only declared bridge types cross the boundary), and runtime (per-isolate heap accounting + cooperative interruption enforce limits).

The host configures, loads, and invokes; the guest sees only whitelisted modules, host bindings, and bridge values.

2. Lifecycle & API surface

The whole module lives under std:engine and must be imported. The core types:

TypeRole
IsolateA sandboxed execution context owning a private heap, GC, registries, policy, bindings, and limits.
UnitA compiled guest compilation unit, loaded into one isolate. Holds the JIT'd module and its public entry table.
PolicyThe capability whitelist (§3). Frozen when the first unit is loaded.
LimitsHard resource caps (§8): heap, allocation budget, wall-clock timeout, stack depth.
StatsMeasured usage of the last invocation / the isolate's lifetime.
LoadErrorCompilation/sandbox failure: a diagnostic list (capability denials, type errors, parse errors).
EngineErrorRuntime failure of an invocation: Timeout, OutOfMemory, GuestPanic{message}, NoSuchEntry, BadArgs.

The lifecycle is configure → load → invoke → observe → dispose:

import { Isolate, Policy, Limits } from "std:engine"
import { println } from "std:io"

// 1. Configure. Builder methods return the isolate for chaining; deny-by-default.
var iso = Isolate.new()
    .allow(["core:collections", "std:io"])     // capability whitelist (§3)
    .bind("host:env", "now", () => clock_ms()) // host binding (§4)
    .limits(Limits {
        max_heap_bytes:  64_000_000,           // 64 MiB hard cap
        max_alloc_bytes: 256_000_000,          // cumulative allocation budget
        timeout_ms:      500,                  // per-invocation wall clock
        max_stack_depth: 2048,
    })

// 2. Load guest source. Compiles inside the isolate under the policy; a forbidden
//    import or a type error returns LoadError without running anything.
var unit = iso.load(guest_source)?            // Unit | LoadError

// 3. Invoke any public entry by name with bridged args (§5, §7).
var resp = await iso.invoke(unit, "handle", [req])   // Resp | EngineError

// 4. Observe.
var s = iso.stats()
println("peak heap=${s.peak_heap_bytes}  elapsed=${s.elapsed_ms}ms")

// 5. Dispose — frees the isolate's heap and registries (also runs on Drop).
iso.dispose()

An Isolate is reusable: a host loads one Unit once and invokes it many times (the edge-function hot path — compile once, run per request). Loading is the expensive step; invocation is a direct JIT call.

3. Capability policy — gating std:/core:/pkg:

An isolate is deny-by-default. With no .allow(...), the guest gets only the implicit prelude syntax (docs/17 §8): built-in control flow, primitive operations, and str methods. Every named symbol — List, println, channel, Thread — must be granted.

Granting toolchain modules

.allow(paths) whitelists built-in module views at the same granularity the language already exposes them (docs/18): a guest may be given std:io but not std:thread, core:collections but not core:ffi.

Isolate.new().allow([
  "core:prelude",        // Iterator, Clone, Eq, Ord, ToStr, panic, ... (usually granted)
  "core:collections",    // List, Map, Set, Entry
  "std:io",              // print, println
  "std:async",           // yield_now, sleep, timeout, AsyncIterator
])

Enforcement is at compile time, the strongest possible form: a guest that writes import { Thread } from "std:thread" when std:thread is not in the whitelist fails to compile and returns a LoadError — it never produces machine code. This reuses the existing import-resolution gate; the policy narrows the set of resolvable built-in views.

Packages and the filesystem

The pkg: and file: schemes are denied outright unless explicitly granted, and an isolate runs in "direct mode" by default where they are already hard errors (docs/17 §13). To grant a vetted dependency the host names it and supplies its source; the engine resolves only the allowed set:

Isolate.new()
    .allow(["core:prelude"])
    .allow_package("json", json_source_tree)   // only "json" is importable as pkg:json
    // file: imports remain denied — no .allow_files(...) call was made
Granularity. The policy gates at the module level, not the symbol level. "Allow std:io but only println, not print" is out of scope — fine-grained per-symbol capabilities would require a capability type system upstream of import resolution. Module-level gating matches how the standard library is already partitioned and is sufficient for sandboxing.

4. Host bindings — virtual modules

The host injects native functions the guest can call by binding them into a virtual module under a host-chosen scheme (host:). The guest imports them like any other module; the engine wires each to the host's implementation.

// Host side — register implementations into a virtual module.
var iso = Isolate.new()
    .allow(["core:prelude"])
    .bind("host:env", "now",    () => clock_ms())
    .bind("host:env", "getenv", (key: str) => lookup_env(key))   // str -> str
    .bind("host:log", "warn",   (msg: str) => { log_warn(msg); null })

// Guest side — import and call them.
import { now, getenv } from "host:env"
import { warn } from "host:log"

function handle(): i64 {
    warn("started at ${now()}")
    now()
}

A binding's implementation is any callable: a host closure (when the embedder is itself Otter code) or a native function (when the embedder is the CLI / a Rust host). The signature is part of the binding and is restricted to bridge-compatible types — primitives, char, bool, str, @Bridge structs, and bridge channel endpoints (§6). This is the same mechanism the macro host uses to expose core:compiler over the AST arena (chapter 22 §8–9), generalized to host-defined modules and signatures.

Host calls run on the host's behalf. A binding is a hole in the sandbox: whatever the host function does (touch the filesystem, the network, a database) happens with the host's privileges, not the guest's. Bind narrowly and validate arguments — bindings are the intended, audited capability surface, so the guest's power is exactly the union of its whitelisted modules and the bindings you give it.

5. The bridge ABI — @Bridge structs

Data crossing the host↔guest boundary uses a declared, stable layout — the same contract as a repr(C) FFI struct (docs/19), not the managed heap. A struct annotated @Bridge has a frozen field layout and crosses by value: its bytes are copied across the boundary per the declared layout. Both sides declare the same @Bridge struct, and the engine validates layout compatibility by the contract (name + field types + order), not by runtime type identity.

@Bridge
struct Request {
    method: str,
    path:   str,
    status: i32,
}

@Bridge
struct Response {
    code:    i32,
    headers: i64,        // bridge-compatible plain-data fields only
    body:    str,
}

Why declared layout instead of shared pointers

Otter Fusion's runtime type identity (type_id) is assigned per compiler instance. The host and a separately-compiled guest assign the same struct different type ids, so passing a managed struct pointer across the boundary would break every type-id-dependent operation (is, as, dynamic dispatch, Drop). Copy-by-value over a declared layout sidesteps this entirely — and, decisively, it keeps the two sides' heaps independent, which is what makes per-isolate heaps and hard memory caps possible. A zero-copy shared pointer would couple host and guest to one GC and forfeit isolation.

What may cross

KindCrosses?How
Primitives (i8..i64, u8..u64, f32/f64, bool, char)✅Passed directly as ABI words.
str✅Copied as bytes into the receiving heap.
@Bridge struct✅Copied field-by-field over the frozen layout. Fields must themselves be bridge-compatible.
Fixed array [T; N] of bridge types✅Copied element-wise.
Bridge channel endpoint (§6)✅By engine-managed handle, not by heap pointer.
Managed List/Map/Set❌Heap-local to an isolate; cross via a @Bridge wrapper, a bridge channel, or by copying into one.
Interface objects, unions, closures, Drop types❌Type-id- or heap-dependent; not bridge-compatible.

The compiler enforces bridge-compatibility where a type is used as a binding parameter, a binding return, or an invoke argument/result: a non-bridge type in those positions is a compile error pointing at the offending field or parameter.

6. Bridge channels & shared state

Copy-by-value covers request/response shapes. For streaming, incremental results, or a long-lived back-channel, the host creates a bridge channel and hands an endpoint to the guest as a bound value. Bridge channels carry bridge-compatible messages and reuse the channel semantics of docs/20 §2 (FIFO, blocking recv, close-on-last-sender), but are managed by the engine layer so they can span the host↔isolate boundary even though each isolate otherwise has its own channel registry (§8).

// Host: make a bridge channel and pass the receiver end into the guest.
var (tx, rx) = iso.bridge_channel<LogLine>()    // (Sender<LogLine>, Receiver<LogLine>)
iso.bind_value("host:log", "sink", tx)           // bind an endpoint as an importable value

spawn drain(rx)                                  // host consumes asynchronously
await iso.invoke(unit, "run", [])                // guest sends through the bound sink

// Guest:
import { sink } from "host:log"
function run() {
    sink.send(LogLine { level: 1, text: "hello" })   // LogLine is @Bridge
}

The final result of an invocation is delivered the same two ways: a bridged return value for a single result (§7), or a bridge channel for a stream of results. Shared<T> (docs/20 §4) may likewise be exposed as a bound value when host and guest need shared mutable state behind the async lock; the shared cell, like a bridge channel, is engine-managed.

7. Invoking any entry — sync & async

Any pub function in the loaded unit is an entry; there is no special main. invoke takes the entry name and a list of bridged arguments, marshals them in, runs the function, and marshals the bridged result out.

// Synchronous entry.
var resp = iso.invoke(unit, "handle", [req])           // Response | EngineError

// Asynchronous entry — the guest function is `async`; the host awaits it.
var resp = await iso.invoke(unit, "handle_async", [req])

// Introspection: discover entries and their signatures before calling.
for e in unit.entries() {
    println("${e.name}(${e.arity}) -> ${e.returns}")
}

Sync and async entries use the same call; the engine detects an async entry (its return type is a Future) and drives it on the isolate's executor, completing the host's await when the guest future resolves. This keeps the language's "no user-visible block_on" rule (docs/21 §6): the host stays in its own async world while the guest runs in the isolate.

An invocation that exceeds a limit, panics, or names a missing entry returns EngineError rather than affecting the host:

match iso.invoke(unit, "handle", [req]) {
    Response r          => serve(r),
    EngineError.Timeout => reply_504(),
    EngineError.OutOfMemory => reply_503(),
    EngineError.GuestPanic p => { log("guest: ${p.message}"); reply_500() },
}

8. Resource control & per-isolate runtime

Hard limits require somewhere to enforce them. The runtime today keeps its heap, GC, and registries in process-global state, which can only support best-effort, process-wide limits. std:engine therefore introduces per-isolate runtime state: each isolate owns its heap, GC budget and threshold, mutator set, channel/Shared/finalizer registries, and allocation accounting. This is the foundation that makes every limit below a genuine per-isolate wall rather than a global heuristic.

The current-isolate context

Every runtime entry point (lang_alloc, the GC safepoint, channel and lock operations, thread/async spawn) is repointed from process-global statics to a per-isolate runtime context. The context is selected by a thread-local current isolate pointer, set when a thread enters an isolate's guest code and cleared on exit — so generated code needs no extra parameter and the hot path stays a thread-local read. Stop-the-world GC operates per isolate (it stops only that isolate's mutators), so one isolate collecting or paused never blocks another.

Limits

LimitEnforcementOn breach
max_heap_bytesChecked in the isolate's allocator against its tracked live + reserved bytes.Allocation fails → OutOfMemory, invocation unwinds.
max_alloc_bytesCumulative allocation counter per invocation.OutOfMemory — bounds total churn even if live set stays small.
timeout_msA deadline checked at the cooperative safepoints codegen already emits (every loop header, before allocation, at native-call boundaries).Timeout — the guest unwinds cleanly at the next safepoint.
max_stack_depthRecursion counter / guard page.GuestPanic (stack overflow), contained to the isolate.
Cooperative interruption fits the existing design. The backend already inserts GC safepoints at every loop back-edge and around blocking calls (docs/16). A deadline / cancel flag checked at those same points gives timeouts and cancellation almost for free: interruption latency is one loop iteration. A straight-line, loop-free, allocation-free snippet is inherently bounded and needs no interruption. The one residual case — a deliberately tight inner loop the optimizer collapsed past a back-edge — is bounded by max_alloc_bytes or, if truly necessary, by running the isolate on a thread the host can abandon.

Measurement

iso.stats() reports per-invocation and lifetime usage: peak and current heap bytes, cumulative bytes allocated, collection count, and wall-clock elapsed. These come directly from the per-isolate heap accounting the limits already maintain.

9. Security model

The guest's authority is exactly the union of (a) its whitelisted built-in/package modules and (b) the host bindings given to it — nothing more. The three enforcement layers compose:

  • Compile-time: a forbidden import never compiles (§3). The strongest layer — denied capabilities produce no code.
  • ABI: only declared bridge types cross the boundary (§5); the guest cannot hand the host (or receive) an arbitrary heap pointer, so it cannot reach into host memory or corrupt host objects.
  • Runtime: per-isolate heap accounting and cooperative interruption enforce memory and time limits (§8); a guest panic, timeout, or OOM is contained and surfaced as EngineError.
Threats this does not cover. The engine bounds resources and capabilities, not micro-architectural side channels (timing, Spectre) or the correctness of host bindings. Treat in-process isolates as a strong defense-in-depth boundary for trusted-but-bounded code and plugins; for fully adversarial multi-tenant workloads, run each isolate (or pool of isolates) in its own OS process behind the same API — the bridge ABI is designed to survive an IPC transport because it never shares heap pointers.

10. Implementation & staging

What the design rests on, and what is new work.

Already exists (the proven substrate)

  • In-process JIT of guest source: backend::compile / compile_with_symbols over a full front-end pass (sema::analyze_multi_ctx).
  • Host-function binding: the macro host registers extern "C" functions + a symbol table into a JIT and exposes them through a virtual module (core:compiler) — the exact template for §4.
  • Calling guest code by name/pointer: Jit::func_ptr; per-entry trampolines follow the macro-shim pattern for §7.
  • Capability gate seam: import resolution already gates schemes via the resolve context; §3 narrows the resolvable built-in views.
  • repr-C struct ABI: extern-struct layout + decorators (docs/19) are the basis for @Bridge (§5).
  • Channels / Shared / async executor (chapters 20–21) back the bridge channels and async-entry driving of §6–§7.
  • Cooperative safepoints at loop headers and native boundaries — the interruption points for §8.

New work

  • planned std:engine prelude surface + host externs (Isolate, Unit, Policy, Limits, Stats, errors).
  • planned The capability-policy field on the resolve context + the per-isolate built-in-view whitelist enforcement.
  • planned @Bridge decorator: layout freeze, bridge-compatibility checking, and field-by-field marshalling in the entry trampolines and bindings.
  • planned Per-entry invocation trampolines + an entry/signature introspection table on Unit.
  • planned Per-isolate runtime state — the largest item: thread a runtime-context handle (selected by a thread-local current-isolate pointer) through every lang_* entry point, so heap, GC, registries, and accounting are per isolate. Enables hard limits and true isolation.
  • planned Limit enforcement: heap/alloc caps in the per-isolate allocator; deadline/cancel flag at safepoints; stack-depth guard.
  • planned Engine-managed bridge channels / Shared cells that span the boundary across per-isolate registries.

Staging keeps each step shippable: (1) a single-isolate load/invoke returning primitives under the capability whitelist; (2) @Bridge structs and str across the boundary; (3) host bindings + bridge channels; (4) per-isolate runtime state; (5) hard limits + stats; (6) async entries. The per-isolate-state phase is the deep one and gates real hard limits — earlier phases run on the shared global heap with best-effort limits and are explicit about it.

11. Summary

  • An isolate runs guest Otter Fusion with its own heap, GC, registries, capability policy, host bindings, and hard limits.
  • Deny-by-default capabilities whitelist built-in modules at module granularity and are enforced at compile time; pkg:/file: are denied unless explicitly granted with vetted source.
  • Host bindings expose native/host functions through virtual host: modules the guest imports — the audited capability surface.
  • Data crosses by @Bridge (repr-C, copy-by-value): a frozen layout validated by contract, never by runtime type id — which is also what keeps the two heaps independent.
  • Bridge channels and bridged return values carry results and streams; Shared<T> exposes shared mutable state.
  • Any pub entry is callable by name, sync or async, with the host driving an async guest future to completion.
  • Per-isolate runtime state makes max_heap_bytes, max_alloc_bytes, timeout_ms, and max_stack_depth real per-isolate walls, with cooperative interruption at existing safepoints and usage reported via stats().
  • Builds on the proven macro-host substrate (chapter 22); the largest new piece is making the runtime isolate-aware.
