21. Async

State-machine futures, JavaScript/Dart-style async / await, a spawn keyword for parallel tasks. No user-visible blocking calls: awaiting suspends the task, never the OS thread; main itself is allowed to be async and the runtime drives the root future.

The two tiers

Shape vs runtime: you can write async on any target; the runtime drives it.

1. Future<T>

pub struct Pending;
pub struct Ready<T> { pub value: T }

pub interface Future<Output> {
  function poll(self, ctx: *Context): Ready<Output> | Pending
}
A Future<T> is inert Calling poll advances it; a future that is never polled never runs. Construction creates a state machine — execution happens only when something drives it. Awaiting a future or spawn-ing it hands the driving job to the executor.

Type ergonomics: Future<null> for "no useful return"; Future<T | E> for fallible async.

2. Context and wakers

extern struct Context {
  waker_data: *u8,
  wake_fn:    extern (*u8) => null,
}
Returning Pending without arranging for a wake is a forever-hung task.

3. async functions

function fetch_data(url: str): Future<str> async {
  var response = await http_get(url)
  response.body
}
Postfix async is a body modifier The async keyword sits between the signature and the body. The return type is written explicitly as Future<T> — there is no auto-wrapping. Calling fetch_data(url) does NOT execute the body — it returns a fresh Future<str>. The compiler turns code between awaits into states.
Interface and impl signatures line up 
interface Fetcher {
  function fetch(self, url: str): Future<str>                  // interface — no body
}

extend MyFetcher: Fetcher {
  function fetch(self, url: str): Future<str> async { ... }    // impl
}
The contract type is identical on both sides; async only annotates the body.

4. await

var v = await fut
  • poll returns Ready<T> → await evaluates to value.
  • poll returns Pending → current async body suspends, returning Pending from its own poll after recording the inner future's waker.
Where await is allowed Only inside an async body (function, closure, or a bare async { ... } block). NOT at module level (only compile-time constants there).
No automatic error propagation If fut: Future<T | E>, the result of await is T | E. Use ? to propagate: (await http_get(url))?.
Precedence await is a prefix unary operator at the same tier as - / ! (row 2 in the precedence table). It binds looser than postfix ?, ., (...), [...], which is why await x? means await (x?) and the propagating form needs parens: (await x)?. await x.field parses as await (x.field); await f(a, b) parses as await (f(a, b)).

5. "Forgot to await" — futures must be captured

A call to an async function returns a Future<T>. The compiler errors when a future is produced as a statement and silently discarded — it would never run, which is almost always a bug. To make a future do anything, you have to do one of:

  • await it from within another async body — drives it to completion;
  • spawn it — hands it to a worker (and returns another Future<T>);
  • bind it (var f = …) and pass it along, or explicitly discard with var _ = ….
function fetch_data(): Future<str> async { "data" }

function main(): Future<null> async {
  fetch_data()             // ERROR — Future created but never used
  spawn fetch_data()       // ERROR — spawn evaluates to a Future too; bind or await
  var h = spawn fetch_data()  // OK — bound
  var _ = fetch_data()     // OK — acknowledged discard
  var s = await fetch_data()  // OK — driven to completion
}
Rule of thumb Every Future a function produces must be either named or consumed before it falls out of statement position. The compiler enforces this.

6. Async main, spawn, and the executor

The program entry can itself be an async function. The runtime detects an async main at startup and drives the root future on the default work-stealing executor. There is no user-visible block_on — sync code cannot "wait" on a future synchronously, because doing so would block the OS thread (which the language forbids).

function main(): Future<null> async {
  var r = await some_top_level_task()
  println(r)
}

The spawn keyword

var f: Future<i64> = spawn work(42);
var v: i64         = await f;

spawn is a prefix keyword (like await). It takes a future-producing expression — usually a call to an async function — hands it to a worker thread, and itself evaluates to a fresh Future<T>. Awaiting that future resolves to the spawned task's result. This mirrors Tokio's JoinHandle, but typed as a Future<T> directly (in the JS/Dart spirit).

Parallel fan-out 
var a: Future<i64> = spawn work(1);
var b: Future<i64> = spawn work(2);
var c: Future<i64> = spawn work(3);
// They all run in parallel. Joining is just awaiting each handle.
var sum: i64 = (await a) + (await b) + (await c);
Don't block the worker thread A future polled by the executor runs on the executor's worker. The poll body must not block the OS thread for long — return Pending and rely on a waker. Synchronous blocking calls (sync file I/O, sync DB) should go through a "blocking task" mechanism the executor provides (implementation-defined).

7. Async closures and inline futures

var f1 = function(x: i64): Future<str> async {
  await sleep(100)
  x as str
}

var f2 = (x) async => {
  await sleep(100)
  x as str
}

// A bare `async { ... }` block is a zero-arg inline future literal — a future
// that captures enclosing locals by value. Useful with `await` / `spawn`:
var h = spawn async { await fetch(); await save(); }

The async modifier sits between the signature and the body opener: before { on a function(...), before => on an arrow closure. The bare async { ... } block is the one exception — a zero-arg inline future literal kept for ergonomics with await and spawn.

Captures follow ordinary closure rules. When passed to spawn, the captured set is subject to cross-thread isolation (20 §1) — captured references are deep-cloned at spawn time. Async closures cannot be extern.

8. Cancellation

Cancellation is explicit. A future exposes a .cancel() method that aborts the underlying state machine and releases I/O registrations synchronously. select!-style combinators call .cancel() on the losing futures when a winner completes.

extend<T> Future<T> {
  function cancel(self)        // aborts the future; safe to call repeatedly
}
Dropping a future does not cancel it promptly Future<T> is a regular GC-managed value. Letting it go out of scope means its Drop impl runs eventually via the finalizer queue — possibly never. If the future holds an I/O registration or a network connection, that resource leaks until the collector observes the future as unreachable and the finalizer thread gets to it.
Always call .cancel() explicitly for futures you no longer want. Treat this like closing a file handle.
No built-in cancellation token For cooperative cancellation deeper in the future's body, pass a Shared<bool> or a Receiver<Cancel> and check it periodically.

9. Timeouts

pub function timeout<T>(fut: Future<T>, duration_ms: i64): Future<T | TimedOut>

pub struct TimedOut;

Races fut against a timer. Whichever finishes first wins; .cancel() is called on the loser.

10. AsyncIterator<T>

pub interface AsyncIterator<T> {
  function next_async(self): Future<Item<T> | Done>
}

function process(stream: AsyncIterator<i64>): Future<null> async {
  for await n in stream {
    println(n as str)
  }
}

Desugaring:

{
  var __it = stream
  loop {
    match (await __it.next_async()) {
      Item { value } => { var n = value; ... loop body ... },
      Done           => break,
    }
  }
}
No generator syntax No yield, no gen. yield is reserved but unused. Implement AsyncIterator<T> by hand: 
pub struct Ticker {
  pub current:  i64,
  pub end:      i64,
  pub delay_ms: i64,
}

extend Ticker: AsyncIterator<i64> {
  function next_async(self): Future<Item<i64> | Done> {
    async {
      if self.current >= self.end {
        Done
      } else {
        await sleep(self.delay_ms)
        var v = self.current
        self.current = self.current + 1
        Item { value: v }
      }
    }
  }
}

11. Async and panics

SiteEffect
async mainProcess exits with the panic; the executor unwinds.
spawn EXPRThe spawned task ends with the panic; await-ing the returned Future<T> propagates the panic at the awaiter.

Other in-flight futures on the same executor are unaffected.

12. Composition primitives — library land

Specific combinators (join, race, select) are stdlib additions, not core language. The minimum guarantees:

  • await exists and behaves as described.
  • spawn is a prefix keyword on a future-producing expression and itself yields a Future<T>.
  • Future<T> has the interface shape above.
  • Context interoperates with C event loops.

13. Summary

  • Future<T> is an inert state machine. JavaScript/Dart-style explicit syntax: async on the body, await at suspension points.
  • Postfix async on a function body produces a Future<T>; await drives one inside another. The return type is written explicitly as Future<T>.
  • Futures must be captured — awaited, spawned, or bound; ignoring one is a compile error.
  • main may itself be async; the runtime drives the root future. There is no user-visible block_on — no blocking calls.
  • spawn EXPR (keyword) schedules a future on a worker and itself returns a Future<T> — perfect for parallel fan-out.
  • AsyncIterator<T> + for await for async streams. No generator syntax.
  • Cancellation via explicit .cancel(); timeouts via timeout(...).
  • Async closures use postfix async too; bare async { ... } is a zero-arg inline future literal.
