1. Project layout

Every project has a manifest at the root and a source root (src/). The manifest's kind picks one of three shapes:

Three project kinds. The compiler walks the mod tree starting at each entry.

2. Module tree & file resolution

One source file = one module. Children are declared with mod. A mod foo in parent.lang resolves to parent/foo.lang — the directory shares the parent's basename.

Top-level exception: mod foo in the entry file (src/lib.lang / src/main.lang / each bins) resolves to src/foo.lang — flat, not nested under src/lib/.

pub mod external, mod private. The compiler errors on any .lang file not reachable from an entry's mod chain.

3. The four path forms

Every import path begins with one of four shapes. The prefix (or its absence) makes the kind unambiguous from a glance:

Four prefix kinds. The shape of the first segment tells you where the path resolves.
FormWhere it resolvesExample
"core:…", "std:…"Toolchain sysroot"std:io"
"pkg:<name>[/sub]"External dependency from manifest"pkg:json/parse"
"seg/seg/…"Absolute inside current package"util/log"
"./x", "../x"Relative to importing file's dir"../shared/util"

The three import forms

Three forms, each contributing something different to the current module. Extensions activate with every form — extend blocks are anonymous and ride along with their defining module.

Three forms, three jobs. Forms compose — you can use all three against the same path.
import "pkg:my_module"                              // ambient — no names bound, extensions activate
import "pkg:my_module" as M                         // namespace bind to M
import { Foo, bar }      from "util/helpers"        // named
import { Foo as Bar }    from "util/helpers"        // named with alias
import { Foo, bar as baz, Qux } from "util/helpers" // mixed
Why a no-names form? extend blocks are anonymous and module-bound — the only way to pick up their methods is to import the defining module. The bare form lets you do that without dumping any names into your namespace.

4. The pub chain

There are two visibility knobs — no pub(crate), no pub(super), no pub(in path):

  • pub item — visible to importers of this module.
  • pub mod — submodule visible to importers of its parent.

For an item to be reachable from outside the package, every mod on the chain must be pub mod AND the leaf item itself must be pub. One missing link breaks the chain.

A single non-pub link in the chain seals off everything below it from outside consumers.

Where pub goes

DeclarationWhat pub exposes
pub mod fooSubmodule visible to importers
pub struct FooThe struct type
pub field inside a structThat field (each field is independent)
pub interface IThe interface
pub function fThe function
pub type T = …The alias
pub var XThe module var (read and write — no read-only modifier)
pub extern functionExported via the C ABI for FFI
pub function … @ProcMacroMacro invokable from other modules
pub import "…" / … as M / { … } from …Re-export (extensions / namespace / names) — see §5
No pub on extend blocks extend blocks are anonymous and module-bound: they activate in any module that imports their defining module (in any of the three forms from §3). The orphan rule keeps the set of possible extension sources small and grep-able.

5. pub import — re-exports

Use pub import to lift individual names out of a private subtree and into your module's public surface. The internal directory tree can be as deep as you like; consumers see a flat public API.

pub import lifts individual names without exposing their containing submodule.
// src/lib.lang
mod internals                                       // private — consumers can't reach internals/*
pub import { Logger } from "internals/log"          // Logger lifted to pkg API
pub import { Db, open } from "internals/db"
pub import "pkg:iter_ext"                           // re-export extension activation (umbrella)
pub import "pkg:json" as Json                       // re-export as namespace
pub import { Foo as Bar } from "util/helpers"       // aliased re-export
  • Simultaneously imports into the current module and re-exports it.
  • Same definition — not a new type, just reachable under a new path.
  • The declaring module itself must still be on a pub mod chain for external reach.
  • Collision rules apply — alias one side with as if needed.
  • The bare form pub import "<path>" makes the target's extensions ambient for any consumer of this module too — the basis of umbrella packages.

6. Built-in modules

Two reserved prefixes identify modules supplied by the toolchain. The name distinction reflects the realistic minimum the language can run on: an allocator is mandatory, but an OS is not.

core:prelude is the only built-in implicitly available; everything else needs an explicit import.

core: (always)

  • core:prelude — operators, iterators, futures, Try, Clone, Drop, ToStr, panic, List, Map, str methods. Auto-imported.
  • core:ffi — c_int, c_void, Foreign.alloc, CStr, with_pin.
  • core:compiler — MacroContext, ASTNode (only in @ProcMacro functions).

std: (needs OS)

  • std:io — print, println, files.
  • std:thread — Thread.spawn, JoinHandle.
  • std:sync — Shared<T>, channels.
  • std:async — spawn, block_on, timeout.
  • std:time, std:fs, std:net.
You cannot Create a module whose path starts with core: or std:, or shadow names from those prefixes. A no-std = true package makes any std:* import a hard error.

7. The package escape boundary

Relative paths (./, ../) are convenient for "next to me" references, but they cannot escape the package. The package boundary is the source root.

Each package is its own escape boundary. The only way to reach another package is its pkg: prefix.

Style guidance (lint, not error) Prefer absolute project paths for cross-cutting modules (logging, types, constants) — the path stays meaningful in error messages and grep results. Prefer relative for tightly-coupled siblings or children — the path stays valid if the subtree moves.
