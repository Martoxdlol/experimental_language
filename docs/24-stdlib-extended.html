24. Standard Library — Extended Roadmap

This chapter extends 18-stdlib with the full proposed standard-library surface. Item status is marked spec (already specified in chapter 18 / elsewhere) or planned (named but not detailed).

Design principle: types live in core:, runtimes live in std: Standardizing data shapes early (HTTP request/response, JSON value, error chains, reader/writer) prevents the JavaScript-style fragmentation where every library invents incompatible types for the same concept. Implementations of those shapes can be third-party.

1. The two tiers, revisited

Chapter 18 introduced two tiers. This chapter splits the core: tier into several modules so that interfaces and value types live close to language semantics, while keeping std: for everything that needs an OS.

Shapes flow downward. Anything in std:* can be replaced by another implementation that satisfies the same core:* interface.

2. Layering: shape vs runtime

The split is rigid:

core: declares

  • Interfaces (contracts)
  • Plain value types (records, unions)
  • Behaviour that needs only an allocator

std: provides

  • OS-bound implementations (files, sockets, clocks)
  • Runtimes (async executor, logger backend)
  • Thread / process primitives

pkg: extends

  • Specific implementations of core:* shapes
  • Alternative runtimes
  • Anything not universal

For example: core:http defines HttpRequest and HttpResponse. A library that ships an HTTP client takes a HttpRequest and returns a HttpResponse. A library that ships an HTTP server consumes HttpRequest. They interoperate without knowing about each other — because the shape is shared.

3. The Request/Response problem

JavaScript's fetch introduced Request and Response late. Before that, every HTTP library shipped its own. The cost compounds:

Standardize the shape; let the implementations compete.

The same logic motivates core:io (Reader/Writer), core:json (the JSON value tree), core:error (the error chain), and std:log (the Logger interface).

4. core:prelude — additions

Chapter 18 leaves the prelude with str, List, Map, Iterator, Item/Done, Buffer, the Error interface + Annotated wrapper, and the numeric helper namespaces. The roadmap removes:

  • List and Map — move to core:collections along with Set.
  • Error, Annotated, with_context — move to core:error.

The prelude gains Deque and Bytes. After the move, the auto-imported surface contains only language-fundamental shapes (text, iteration, FFI bytes, numeric helpers).

Why explicit collections List<T> and Map<K, V> are heap-allocated, GC-managed containers. Pulling them out of the prelude makes their use visible at every import site rather than implicit. It also keeps the auto-imported surface minimal: the prelude after this change contains language-fundamental shapes only (text, iteration, FFI bytes, numeric helpers).

5. core:collections — List · Map · Set

Explicit-import module within the core: tier. Holds the three heap-allocated, GC-managed general-purpose containers.

import { List, Map, Set } from "core:collections"

var xs: List<i64>     = [1, 2, 3]
var m:  Map<str, i64> = { "x": 1 }
var s:  Set<str>      = { "a", "b" }
Literal syntax still works without prelude The literal forms [...], { k: v, ... }, and { a, b } are language-level syntax (chapters 1 & 18). They construct the corresponding container type — but the name List / Map / Set must still be imported to write type annotations, call static constructors, or use the type-as-constructor shorthand.

List<T>

Dynamic array. Full definition in 18.3; the only change here is module location.

6. core:io — Reader · Writer · Seeker

The single most load-bearing addition. Every I/O source/sink in std: implements these three interfaces, so parsers, encoders, compressors, and protocol code written against the interfaces work on files, sockets, in-memory buffers, and stdin/stdout uniformly.

pub interface Reader {
  // Reads up to buf.size() bytes. Returns bytes-read, or 0 on EOF, or IoError.
  function read(self, buf: Bytes): i64 | IoError

  // Convenience: read until EOF, append to buf. Default impl provided.
  function read_to_end(self, buf: Bytes): i64 | IoError
}

pub interface Writer {
  function write(self, buf: Bytes): i64 | IoError
  function write_all(self, buf: Bytes): null | IoError
  function flush(self): null | IoError
}

pub interface Seeker {
  function seek(self, pos: SeekFrom): i64 | IoError
}

pub union SeekFrom = Start { offset: u64 }
                   | Current { offset: i64 }
                   | End { offset: i64 }

pub struct IoError {
  pub kind: IoErrorKind,
  pub message: str,
}

pub union IoErrorKind = NotFound | PermissionDenied | ConnectionRefused
                      | TimedOut | UnexpectedEof | Interrupted | Other

Buffered variants

pub struct BufReader<R: Reader> { ... }
extend<R: Reader> BufReader<R>: Reader {
  function new(inner: R): BufReader<R>
  function with_capacity(cap: i64, inner: R): BufReader<R>
  function read_line(self): str | IoError      // up to '\n' inclusive; '' on EOF
  function lines(self): Iterator<str | IoError>
}

pub struct BufWriter<W: Writer> { ... }
extend<W: Writer> BufWriter<W>: Writer {
  function new(inner: W): BufWriter<W>
}
Why this lives in core: None of these depend on the OS. A no-OS target can implement Reader for a ROM-backed byte source and write portable parsers against it. The OS-bound concrete handles (files, sockets) live in std:io / std:fs / std:net.

7. core:fmt — Display & Debug

Chapter 18 notes that there is no formatting machinery. The roadmap adds the minimum needed to prevent every library inventing its own stringification. The existing ToStr interface (§15) becomes the Display output path.

// User-facing string form. Re-export of the existing ToStr interface.
pub interface Display {
  function display(self): str
}

// Developer-facing form. Distinct from Display so logging / debug output
// can show types differently from how they appear to end users.
pub interface Debug {
  function debug(self): str
}

// Sink for incremental writes — usable with anything implementing Writer
// or with a Bytes buffer.
pub interface FmtSink {
  function write_str(self, s: str): null | FmtError
}

pub struct FmtError { pub message: str }

Implementations of Debug for built-in types: i32, f64, str, List<T: Debug>, Map<K: Debug, V: Debug>, etc.

Format strings are still out No format! macro is added. String interpolation (chapter 1) is the only formatting sugar. Display / Debug exist purely so libraries can agree on how to stringify a value when interpolation is not enough.

8. core:error — error interface

The Error interface and the Annotated wrapper are spec'd in chapter 18 (§18.3) and live in core:prelude today. This roadmap moves them out of the prelude into a dedicated core:error module — same definitions, explicit import.

// Re-spec from 18.3, unchanged shape:
pub interface Error: ToStr {
  function message(self): str
  function cause(self): Error | null
}

pub struct Annotated {
  pub note:   str,
  pub source: Error,
}

extend Annotated: Error {
  function message(self): str          { self.note }
  function cause(self):   Error | null { self.source }
  function to_str(self):  str          { self.note + ": " + self.source.to_str() }
}

pub function with_context<T, E: Error>(
  value: T | E,
  note: str,
): T | Annotated
Conventions (recap from chapter 13)
  • Libraries define their own error structs, then extend them with Error. They still appear in unions (T | MyError); the interface just lets them flow into generic error-handling code.
  • ? (chapter 13) continues to work on unions; this module adds nothing to its rules.
  • Logging and tracing libraries accept any Error without knowing the concrete type, and call to_str() to render.
  • No Display / Debug split — ToStr (chapter 15) is the only stringification path, so Error: ToStr alone is enough.

10. core:hash — Hasher

The existing Hash interface (§15) hashes a value into a 64-bit number. That hides which hasher is used. core:hash exposes the hasher so users can pick deterministic / cryptographic / fast variants.

pub interface Hasher {
  function write(self, bytes: Bytes): null
  function write_u8(self, n: u8):   null
  function write_u64(self, n: u64): null
  function finish(self): u64
}

pub interface Hash {
  function hash<H: Hasher>(self, h: H): null
}

// Default hasher. Implementation-defined (SipHash-1-3 or similar). Randomized per-process.
pub struct DefaultHasher { ... }
extend DefaultHasher: Hasher { ... }
extend DefaultHasher {
  function new(): DefaultHasher
}

// Deterministic / fast / cryptographic variants are pkg:-tier.

The shape of Hash changes slightly from §15: it now writes into a hasher rather than returning u64 directly. Map and Set construct a DefaultHasher internally.

11. core:async — shapes only planned

Chapter 21 introduces Future, Ready, Pending, Context, and AsyncIterator in core:prelude. The roadmap pulls them into their own module core:async so they can be referred to without polluting the prelude.

pub interface Future<T> {
  function poll(self, ctx: Context): Ready<T> | Pending
}

pub struct Ready<T> { pub value: T }
pub struct Pending;

pub struct Context { ... }    // opaque; constructed by executor

pub interface AsyncIterator<T> {
  function poll_next(self, ctx: Context): Ready<Item<T> | Done> | Pending
}

Re-exported from core:prelude for ergonomics. std:async provides the executor that drives them.

14. core:http — Method · Status · Headers · Request · Response

The single most important fragmentation defense. Implementations of clients and servers live in pkg: or are layered on std:net; the types are universal.

pub union Method = Get | Head | Post | Put | Delete | Patch
                 | Options | Trace | Connect
                 | Custom { name: str }

pub struct Status {
  pub code: u16,                    // 100 .. 599
  pub reason: str | null,           // null means default for code
}

extend Status {
  function ok():           Status   // 200
  function created():      Status   // 201
  function no_content():   Status   // 204
  function not_found():    Status   // 404
  function internal_err(): Status   // 500
  function is_success(self):     bool       // 200..300
  function is_redirection(self): bool       // 300..400
  function is_client_error(self): bool      // 400..500
  function is_server_error(self): bool      // 500..600
}

pub struct Headers {
  // Case-insensitive multi-map. Stores last-write-wins per name for `get`,
  // exposes all values via `get_all`.
}

extend Headers {
  function new(): Headers
  function get(self, name: str):     str | null
  function get_all(self, name: str): List<str>
  function set(self, name: str, value: str): null
  function append(self, name: str, value: str): null
  function remove(self, name: str):  null
  function contains(self, name: str): bool
  function iter(self): Iterator<Entry<str, str>>
}

pub struct HttpRequest {
  pub method:  Method,
  pub url:     Url,
  pub headers: Headers,
  pub body:    Bytes,
  pub version: HttpVersion,
}

pub struct HttpResponse {
  pub status:  Status,
  pub headers: Headers,
  pub body:    Bytes,
  pub version: HttpVersion,
}

pub union HttpVersion = Http10 | Http11 | Http2 | Http3
Composability A middleware function signature like function (req: HttpRequest, next: (HttpRequest) => HttpResponse): HttpResponse works across any client and any server in the ecosystem, because the types are pinned in core:http.

What is still out

  • Regex — community responsibility. A pkg: crate is expected to ship a Regex type built on str.
  • JSON parser / serializer — community responsibility. The value type is standardized; the parser is not.
  • HTTP client / server — community responsibility. The types are standardized in core:http; the wire implementation is not.
  • Crypto primitives — community responsibility (SHA-256, AES, HMAC, …).
  • TLS — community responsibility, layered on std:net.
  • Compression — community responsibility (gzip, zstd, …).
  • UUID — likely a small pkg: crate; could be promoted to core: later if usage warrants.
  • BigInt / Decimal — community responsibility; revisit if scientific / finance usage emerges.
  • Format strings (format!) — string interpolation (§1) covers the common case.
