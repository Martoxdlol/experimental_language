13. Error Handling

No exceptions. No try/catch. Errors are union variants; the postfix ? propagates them; the Error interface gives them a shared shape; panic handles truly unrecoverable cases.

1. Errors as union variants

struct Error {
  pub message: str,
  pub code: i32,
}

function divide(a: f64, b: f64): f64 | Error {
  if b == 0.0 {
    Error { message: "Division by zero", code: 1 }
  } else {
    a / b
  }
}

function main(): Future<null> async {
  var r = divide(10.0, 2.0)
  match r {
    f64 v   => await print("ok: " + (v as str)),
    Error e => await print("err: " + e.message),
  }
}

2. The ? operator

Postfix early-return propagation. The compiler partitions expr's type into success and failure sets based on the enclosing function's return type R:

Partition is by static type assignability to R — failure variants get returned; success variants flow on.
function read_user(id: i64): User | NotFound | DbError { ... }

function summary(id: i64): str | NotFound | DbError {
  var user = read_user(id)?   // ? handles NotFound and DbError; user: User here
  user.name
}
When partitioning fails — three errors
  • Success set empty → "the expression always returns; use a direct match instead".
  • Failure set empty → "nothing to propagate; remove the ?".
  • Some variants neither in R nor strictly successful → "variant X can't propagate; widen R or handle X".

Chained ?

function load_config(): Config | IoError | ParseError { ... }
function validate(c: Config): Config | ValidationError { ... }

function start(): str | IoError | ParseError | ValidationError {
  var c = load_config()?    // strips IoError | ParseError
  var v = validate(c)?      // strips ValidationError
  "ok: " + v.name
}

3. The Try interface — custom propagation

For types that are not unions but want to participate in ? (e.g. a wrapper struct), implement Try:

pub interface Try<Output, Residual> {
  function branch(self): Output | Residual
}

// Usage on v: T where T: Try<O, R>:
v?
// desugars to:
{
  var t = v.branch()
  if t is R { return t }       // possibly with FromResidual conversion
  t as O
}
Built-in for unions The compiler provides a built-in Try impl for unions that performs the partitioning from §2. User code does not implement Try for unions.

4. Residual conversion — FromResidual

When a function returns an error type that is almost what ? would propagate but not exactly, FromResidual lets the compiler insert a conversion.

Direct propagation > FromResidual > compile error.
pub interface FromResidual<R> {
  function from_residual(r: R): Self
}
No automatic null → Error conversion FromResidual<null> is not auto-implemented for any Error-type. A function that calls a T | null API but returns T | E must lift explicitly: 
function head(list: List<User>): User | NotFound {
  var first = list.get(0)              // User | null
  if first is null { return NotFound }
  first as User
}
This keeps the "no reason" vs "with reason" choice deliberate. If you want it implicit for a given error type, write the impl yourself: extend MyError: FromResidual<null> { ... }.

5. The Error interface & Annotated

Errors are still ordinary values living in unions. What the Error interface (defined in chapter 18, imported from std:error) gives you is a shared shape across libraries — so loggers, panic-helpers, and context-wrappers can consume any error without knowing its concrete type.

pub interface Error: ToStr {
  function message(self): str
  function cause(self): Error | null
}

Error: ToStr means every error is also stringifiable through the language's single ToStr path (chapter 15). message(self) is this layer's short text; cause(self) walks the chain.

Canonical error shapes

Two layouts. Pick whichever matches the failure modes you expose.

Kinded — multiple failure modes the caller may discriminate. 
pub struct IoError {
  pub kind:    IoErrorKind,
  pub message: str,
}

pub type IoErrorKind =
    NotFound | PermissionDenied
  | ConnectionRefused | IoTimedOut
  | UnexpectedEof | Interrupted
  | OtherIo
Flat — one failure mode plus optional payload. 
pub struct ParseError {
  pub message:  str,
  pub position: i64,
}
Forward-compatibility rule for kinded errors Include a catch-all variant in every public *Kind union (for example, OtherIo in std:io.IoErrorKind), and always handle it with an else => arm in match. Adding new variants later is then non-breaking for any caller following the rule.

Annotating errors — Annotated + with_context

To attach a breadcrumb when crossing a layer boundary, wrap any error with Annotated. The wrapped value is itself an Error, so chains nest:

pub struct Annotated {
  pub note:   str,     // this layer's contribution
  pub source: Error,   // the wrapped lower-level error
}

// Helper: lift a fallible result, attaching context only on failure.
pub function with_context<T, E: Error>(
  value: T | E,
  note: str,
): T | Annotated

Annotated implements std:fmt.Debug for diagnostics. It does not implement generic clone, equality, or hash because the wrapped source is only guaranteed to implement Error.

not carry source-location info — see "No backtraces on errors" below.
Chains are explicit, bottom-up, allocation-cheap — and grep-able like any other call.
function load(path: str): Config | Annotated {
  var bytes  = with_context(read_file(path),     "loading config")?
  var parsed = with_context(parse(bytes),        "parsing config")?
  with_context(validate(parsed),                 "validating config")?
}
No backtraces on errors Value-errors do not capture file/line at construction — this would impose hidden allocations on every fallible call. Debug-build panics still print stack traces (chapter 14). For value-errors, the explicit Annotated chain plays the same role: each with_context at a propagation site is a deliberate breadcrumb. Tooling that wants real captured locations can add a field to its own error struct.

6. When to use T | null vs T | E

Both shapes exist for a reason. The rule:

ShapeUse when…Examples
T | null Failure carries no information beyond "absent or invalid input". The caller does not need to render why it failed. Map.get, List.pop, str.index_of, parse_int (when "not a number" is the whole story).
T | E where E: Error Failure has a reason the caller may render, log, branch on, or enrich with context. read_file, connect, parse_config, authenticate.
panic The condition violates an invariant the caller is responsible for upholding — a programming bug, not a runtime failure path. Indexing past List.size(), division by zero, as on a variant that doesn't match.
No blessed Result<T, E> alias Chapter 3 shows type Result<T, E> = T | E works as a generic union. The stdlib does not ship it. Write T | E directly. The reason is pedagogical: the language's failure model is the union — wrapping it in a named alias hides what's going on without adding power.

7. No exceptions, no unwinding

What's missing — on purpose
  • No exception types or throw.
  • No try/catch/finally.
  • No stack-unwinding errors that bubble through frames silently.
Every error is either returned as a value (? or matched) or triggered as a panic (kills the thread). You can grep for ? to see every site that may return early.

8. Panics are not catchable

panic(...) and panic-on-failure operations (as mismatch, integer ÷ by zero, etc.) terminate the current thread. They are not catchable. Use them only for programming bugs and truly unrecoverable conditions; use T | Error + ? for expected error paths. See 14-panics.

9. Style guidance

Default practices
  • One error type per module boundary. A public API exposes one Error-implementing struct (e.g. AppError) and uses FromResidual to absorb lower-level errors.
  • Pick the canonical shape. Use the kinded layout ({ kind, message, ... }) when callers may discriminate; flat when there is one failure mode plus payload.
  • Always include a catch-all variant in a public *Kind union and always use else => in match on it. Adding variants later is then non-breaking.
  • Annotate at boundaries. Wrap with Annotated / with_context(...) at the layer that has the context to add. Don't wrap at every ? — only where the breadcrumb is meaningful.
  • ? first, match when you need to discriminate. Reserve match for branching on failure kind.
  • Keep public unions narrow. More than ~5 error variants in an exported return type is a signal to collapse via FromResidual.
  • Panics are for invariants, not flow. Use T | E / ? for any failure mode a caller might handle.
  • Pick T | null only when failure carries no reason. See §6 — and don't lift implicitly into T | Error.

10. Examples

// === Lower-level error types ===
pub struct IoError {
  pub kind:    IoErrorKind,
  pub message: str,
}
pub type IoErrorKind = NotFound | PermissionDenied | OtherIo

pub struct ParseError {
  pub message:  str,
  pub position: i64,
}

extend IoError: Error {
  function message(self): str          { self.message }
  function cause(self):   Error | null { null }
  function to_str(self):  str          { "io: " + self.message }
}
extend ParseError: Error {
  function message(self): str          { self.message }
  function cause(self):   Error | null { null }
  function to_str(self):  str          { "parse@" + (self.position as str) + ": " + self.message }
}

function read_file(path: str): str    | IoError    { ... }
function parse(s: str):         Config | ParseError { ... }

// === Option A: propagate the raw union ===
function load(path: str): Config | IoError | ParseError {
  var s = read_file(path)?       // strips IoError
  parse(s)?                      // strips ParseError
}

// === Option B: collapse into a single module-level error via FromResidual ===
pub struct AppError {
  pub kind:    AppErrorKind,
  pub message: str,
}
pub type AppErrorKind = Io | Parse | Validation | Other

extend AppError: Error {
  function message(self): str          { self.message }
  function cause(self):   Error | null { null }
  function to_str(self):  str          { self.message }
}

extend AppError: FromResidual<IoError> {
  function from_residual(e: IoError): AppError {
    AppError { kind: Io, message: e.to_str() }
  }
}
extend AppError: FromResidual<ParseError> {
  function from_residual(e: ParseError): AppError {
    AppError { kind: Parse, message: e.to_str() }
  }
}

function load_wrapped(path: str): Config | AppError {
  var s = read_file(path)?       // IoError  → AppError via FromResidual
  parse(s)?                      // ParseError → AppError via FromResidual
}

// === Option C: keep the chain visible via Annotated breadcrumbs ===
function load_with_breadcrumbs(path: str): Config | Annotated {
  var bytes  = with_context(read_file(path),  "loading config")?
  var parsed = with_context(parse(bytes),     "parsing config")?
  with_context(validate(parsed),              "validating config")?
}
// Calling load_with_breadcrumbs and walking .cause() yields the full chain.
