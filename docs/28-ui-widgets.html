28. UI Framework — Widgets, Elements & Reactivity design

The user-level API of std:ui: a declarative, reactive UI in the spirit of Flutter, written in idiomatic Otter Fusion. A widget is an ordinary struct that extends the Widget interface; state is a remembered Cell<T> obtained from the build context; children are a List<Widget>. Two authoring forms share one runtime — a fully explicit manual form (just struct + extend, no macros) and an optional @Component decorator macro that adds Compose-style brevity by expanding to exactly that manual form. The catalog and names are Flutter's; layout is Flutter's own constraint protocol (chapter 27 §2); the reactive core is surgical recomposition — a state change re-runs only the scopes that read it.

1. Scope & the chapter-27 contract

Chapter 27 delivered a frame pipeline (build → layout → paint → composite → raster), a persistent render tree and layer tree, a Canvas interface, deterministic native-handle lifetimes, and five engine hooks for skipping clean work (§12.1). This chapter adds the widget layer (the declarative config the user writes), the element layer (the persistent instance tree that reconciles configs and owns state), and the reactive model (how a state change marks the build dirty set, and how narrowly).

2. The three trees, from the top

Three parallel trees, as in Flutter. The user authors only the first; the framework manages the other two. Each is an interface object — the bare interface name used as a value type (docs/10 §8), exactly like var a: Shape = Square { … } in the dynamic-dispatch example.

3. Built from Otter Fusion idioms

Every construct in this chapter is an existing language feature, used the way the examples in examples/ use it:

The one interface

A widget implements a single interface — there is no stateless/stateful class split, because state is a remembered cell from the context (§6), so a "stateful" widget is just one whose build calls ctx.state(…):

interface Widget {
  function build(self, ctx: BuildContext): Widget;
}

Leaf and render widgets (Text, Container, …) are framework structs that also implement Widget; their build produces a render object instead of a child widget (the element layer handles the distinction). User code almost always writes composition widgets whose build returns other widgets.

4. Authoring (1): the manual form

Nothing but struct + extend. This always works, macros or not.

Stateless

import { Widget, BuildContext } from "std:ui";
import { Text } from "std:ui";

struct Greeting { name: str }

extend Greeting: Widget {
  function build(self, ctx: BuildContext): Widget {
    Text("hello, ${self.name}")
  }
}

var g: Widget = Greeting { name: "Ada" };   // struct literal = the language's "named args"

Stateful

State is a Cell<T> from ctx.state(initial) — remembered for the element's lifetime, so each rebuild gets the same cell. .get() reads (and subscribes the current scope, §6); .set()/.update() writes (and marks subscribers dirty).

import { Widget, BuildContext } from "std:ui";
import { Column, Text, Button } from "std:ui";

@Derive(Eq)                       // lets the reconciler skip this subtree when `start` is unchanged
struct Counter { start: i64 }

extend Counter: Widget {
  function build(self, ctx: BuildContext): Widget {
    var count = ctx.state(self.start);          // Cell, remembered across rebuilds
    Column { children: [
      Text("count: ${count.get()}"),                                  // read → subscribe
      Button { label: "+", on_tap: () => { count.update((n: i64) => n + 1) } },  // write → notify
    ] }
  }
}

Every line is plain Otter Fusion: an extend … : Widget implementation with a self receiver, a struct-literal Column { children: [...] }, a tuple-struct Text(...), a record-struct Button { … } whose on_tap field is a block-bodied closure, and Cell methods. No macro is involved.

5. Authoring (2): the @Component macro

@Component is a decorator macro (chapter 22) that writes §4 for you and expands to exactly that manual form. It is the only place the Compose-style sugar — bare-children blocks, state() with plain reads/writes — appears, because the macro rewrites the body it owns.

import { Component } from "std:ui";
import { Column, Text, Button } from "std:ui";

@Component
function Counter(start: i64) {
  var count = state(start)            // remembered Cell
  Column {
    Text("count: ${count}")                          // rewritten to count.get()
    Button { label: "+", on_tap: () => { count = count + 1 } }  // rewritten to count.set(count + 1)
  }
}

var c: Widget = Counter { start: 10 };   // call site stays a struct literal

The macro generates, and you could otherwise hand-write:

  1. the config struct from the parameters, with @Derive(Eq, Hash) and a defaults() static for spread construction;
  2. the extend … : Widget implementation with the build body;
  3. state binding — var x = state(…) → var x = ctx.state(…), with x reads rewritten to x.get() and x = e statements to x.set(e) (the write must be an assignment statement in a block — the macro rewrites it; it cannot invent +=, which the lexer has no token for);
  4. content-block collection — bare widget statements inside a layout's trailing block become its children: [...];
  5. recompose-scope boundaries at child/control-flow points, plus const-scope hoisting (chapter 27 §12.2).
The macro is sugar, never new grammar. Call sites stay struct literals; there are still no named call arguments and no +=. Its leverage is purely desugaring within legal syntax — collecting block statements and rewriting tracked-cell access — so the framework works identically with macros disabled.

6. Reactive state & surgical recomposition

Identical semantics in both forms; the macro just hides .get()/.set(). The mechanism is a reactive cell plus scope-level auto-tracking.

6.1 The reactive cell

struct Cell<T> { /* value + subscriber scopes — framework-internal */ }

extend<T> Cell<T> {
  function get(self): T { /* records: current scope depends on this cell */ }
  function set(self, v: T) { /* marks subscriber scopes dirty; requests a frame (ch.27 §7) */ }
  function update(self, f: (T) => T) { self.set(f(self.get())) }
}

ctx.state(initial) creates such a cell the first time a scope runs and returns the same one on every later rebuild (it is remembered on the element). get during a scope's execution records the dependency; set marks exactly the dependent scopes.

6.2 Recompose scopes — the unit of recomputation

A scope is a build fragment delimited at child / control-flow boundaries. In Counter, the Text and the Button are separate scopes. A write re-runs only the scopes that read the cell:

   count.update((n) => n + 1)
        │  cell notifies its subscriber scopes
        ▼
   dirty scopes = { Text-scope }              ← Button never called count.get()
        │  request_frame()
        ▼
   FRAME: re-run ONLY the Text scope → new Text("count: 1")
        │  reconcile new Text vs old Text element  (§8)
        ▼
   RenderParagraph text changes → repaint boundary re-records just that;
   the Column layout and the Button are untouched
A write re-runs only the scopes that read the cell — not the whole build, not sibling scopes.

6.3 Soundness & the escape hatch

Dirty marking is driven by observed get() calls, not static analysis, so any path from a cell to a scope creates the subscription when that scope runs; a scope that never reads a cell is provably independent of it. ctx.rebuild_all() opts a region into coarse, whole-build recomposition where fine-grained splitting is undesirable. Fine-grained is the default; coarse is explicit.

7. The build context

BuildContext is the handle to an element's position in the tree, passed to build (and threaded implicitly by the macro). It is the user's window onto the element layer:

MethodPurpose
ctx.state<T>(initial): Cell<T>create/recall a remembered reactive cell (§6)
ctx.watch<T>(): Tread inherited state and subscribe the current scope (§11)
ctx.read<T>(): Tread inherited state once, no subscription
ctx.derived<T>(compute): Cell<T>a computed cell (§12)
ctx.size(): Sizethis element's render size (valid post-layout)
ctx.rebuild_all()opt this build out of scope tracking (§6.3)

A BuildContext is valid only during build/lifecycle of its element; an escaped use is rejected the way the escape-analysis pass rejects an escaped Shared lock reference (chapter 20 §4).

8. Reconciliation, keys & element lifecycle

Each frame, a (re-built) widget subtree reconciles against the existing element subtree:

  1. Same slot, compatible widget (same struct type and key) → update in place: the element keeps its identity and remembered cells; its widget config is replaced. If the new config == the old (via @Derive(Eq), §3), the subtree is skipped entirely.
  2. Incompatible → unmount the old subtree (running effect cleanups + dropping render objects, deterministic via @RefCounted) and mount a fresh one.
  3. Lists of children → matched by key first, then position, so a reordered/inserted keyed child moves its element (and cells) instead of rebuilding.
// Build the child list with `.map { it }` (trailing closure + implicit `it`, docs/09 §6) —
// `Key.of(...)` is a static method; no list-comprehension grammar is needed.
Column { children:
  self.items.map { TodoRow { key: Key.of(it.id), item: it } }
}

Lifecycle: initial → mounted → (updated)* → defunct. Because render objects holding native peers are @RefCounted (chapter 27 §11), unmounting a subtree releases GPU resources deterministically — Flutter's dispose() contract, automatic.

9. Effects & lifecycle

Side effects bound to an element's lifetime are registered from build via context methods that take closures. They subsume initState/didUpdateWidget/dispose:

EffectRuns
ctx.on_mount(body)once, after first insertion
ctx.launched(keys, async_body)spawns a task on enter; cancelled on leave or key change
ctx.effect(keys, body) where body returns a cleanup closureon enter / key change; cleanup runs before re-run and on unmount
 
@Component
function Clock() {
  var now = state(Instant.now())
  ctx.launched([]) {
    while true {
      var _ = await sleep(Duration.ms(1000));
      now = Instant.now()                      // marks only the Text scope below
    }
  }                                            // the task is cancelled when Clock leaves the tree
  Text("now: ${now}")
}

A launched task's cancellation is tied to the element's lifetime: leaving the tree cancels it cooperatively at the next await, running its drops and releasing held locks/endpoints via the per-task release path (chapter 21 §8). The same path releases an effect cleanup closure and any @RefCounted resource it captured.

10. Composable logic — hooks

The context methods of §6–§9 (ctx.state, ctx.effect, ctx.derived, ctx.remember) are hooks in the React sense: functions that attach per-element state to the current build. So composable logic — extracting and reusing stateful behavior across widgets — needs no new runtime: a custom hook is an ordinary function that takes the BuildContext and calls other hooks. Flutter has no native equivalent (it relies on the third-party flutter_hooks); this is closer to React/Compose, and falls out of the model already in place.

Custom hooks are just functions

// Composable logic: track window size, with cleanup. Reusable in any widget.
function use_window_size(ctx: BuildContext): Cell<Size> {
  var size = ctx.state(Window.size());
  ctx.effect([], () => {
    var sub = Window.on_resize((s: Size) => { size.set(s) });
    () => { sub.cancel() }            // block's trailing expr = the cleanup closure
  });
  size
}

// A hook returning state PLUS callbacks — bundle them in a struct.
struct CounterApi { value: Cell<i64>, inc: () => null, dec: () => null }

function use_counter(ctx: BuildContext, start: i64): CounterApi {
  var v = ctx.state(start);
  CounterApi {
    value: v,
    inc: () => { v.update((n: i64) => n + 1) },
    dec: () => { v.update((n: i64) => n - 1) },
  }
}

Hooks compose with effects, async, and unions — a data-fetching hook:

struct Loading {}
struct Ready<T> { value: T }
struct Failed { error: str }
type Async<T> = Loading | Ready<T> | Failed;

function use_fetch<T>(ctx: BuildContext, url: str, parse: (str) => T): Cell<Async<T>> {
  var state = ctx.state(Loading {});
  ctx.launched([url], async () => {        // re-runs when `url` changes (keyed)
    var body = await http_get(url);
    match body {
      str b       => state.set(Ready { value: parse(b) }),
      HttpError e => state.set(Failed { error: e.message }),
    }
  });
  state
}

Consuming a hook is a call inside build; because each hook's Cell subscribes the reading scope (§6), surgical recomposition still applies per-fragment:

extend Header: Widget {
  function build(self, ctx: BuildContext): Widget {
    var size = use_window_size(ctx);
    Text("width: ${size.get().width}")
  }
}

Inside a @Component body the context is ambient, so the same call reads var size = use_window_size().

Hook identity — how a hook finds its slot

ctx.state(init) must return the same cell on every rebuild. How a call is matched to its slot is the one design decision, and it sets whether the "rules of hooks" apply. The chosen model mirrors the manual/macro split of §4–§5:

FormIdentityConstraint
Manual (no macro)positional — a per-build hook cursor, reset each build (React's model)call hooks unconditionally, in stable order (no hooks inside if/for); use the explicit-key escape ctx.state_keyed(key, init) when you must
@Component / @Hooklexical call-site key — the macro stamps each hook call site with a stable key (Compose's model)conditionals are allowed; a hook in a loop takes a key per iteration

A custom hook annotated @Hook (the sibling of @Component) gets the ambient context and the lexical-key treatment, and the compiler verifies hook usage — reporting any violation on real source (the span discipline of chapter 22). A plain function …(ctx: BuildContext) is the always-works manual baseline, governed by the positional rules above. Either way a hook's identity is the (call-site, loop-key) pair, so the lexical-key form is strictly more permissive than React's call-order.

Why this fits. Hooks add no engine machinery — every hook bottoms out in ctx.state/effect/derived, whose cells already drive surgical recomposition (§6). The only new pieces are the hook cursor (manual) and the @Hook macro's call-site keying + usage verification, which reuse @Component's machinery (§5).

The built-in hooks

Custom hooks compose the primitives already specified: ctx.state (§6), ctx.derived / ctx.remember (§12), ctx.effect / ctx.launched / ctx.on_mount (§9), and ctx.watch / ctx.read (§11).

11. Inherited state & dependency injection

Cross-tree shared state uses an Inherited<T> widget — Flutter's InheritedWidget — placed above a subtree and read via the context:

Inherited<Theme> { value: dark_theme, child:
  AppBody {}        // below: ctx.watch<Theme>() reads dark_theme AND subscribes this scope
}

The improvement over Flutter: ctx.watch<T>() subscribes at scope granularity through the same cell mechanism as ctx.state() (§6), so when the inherited value changes only the scopes that actually called watch<T>() re-run — not every descendant below the provider. ctx.read<T>() is the no-subscription variant.

12. Derived values & remember

  • ctx.remember(compute) — run compute once, reuse across rebuilds (keyed variant ctx.remember(keys, compute) recomputes on key change). For expensive non-reactive setup.
  • ctx.derived(compute) — a computed Cell<T> that recomputes only when a cell it reads changes; reading it subscribes the reader.
extend NameTag: Widget {
  function build(self, ctx: BuildContext): Widget {
    var first = ctx.state(self.first);
    var last  = ctx.state(self.last);
    var full  = ctx.derived(() => "${first.get()} ${last.get()}");  // recomputes only on first/last change
    Text(full.get())
  }
}

derived generalizes the paragraph/picture memoization the engine already does (chapter 27 §10, §12.1 picture memo).

13. Gestures & hit testing

Pointer input arrives batched on the embedder entry point (chapter 27 §6) and is decoded into a union, then routed by hit-testing the render tree (each render object reports whether a point is inside it, building a hit path):

type PointerEvent = PointerDown | PointerMove | PointerUp | PointerCancel;

function dispatch(target: GestureRecognizer, e: PointerEvent) {
  match e {
    PointerDown d => target.on_down(d.position),
    PointerMove m => target.on_move(m.delta),
    PointerUp u   => target.on_up(u.position),
    PointerCancel => target.on_cancel(),
  }
}

GestureDetector turns the recognized stream into callbacks:

GestureDetector {
  on_tap: () => { count.update((n: i64) => n + 1) },
  on_pan_update: (delta: Offset) => { offset.set(offset.get().add(delta)) },
  child: Container { ..Container.defaults(), width: 80.0, height: 80.0, color: Color.blue },
}

A gesture arena resolves competing recognizers (tap vs pan vs scroll) like Flutter's; recognizers run on the executor, never blocking the platform thread.

14. Animation & the ticker

Animations are driven by a ticker bound to vsync (chapter 27 §7): each frame, active controllers advance and feed reactive cells, marking only the dependent scopes dirty.

extend FadeIn: Widget {
  function build(self, ctx: BuildContext): Widget {
    var t = ctx.animate(0.0, 1.0, Duration.ms(300));   // remembered controller → Cell
    Opacity { opacity: t.get(), child: Text("fading in") }   // only this scope re-runs per frame
  }
}

The controller is remembered for the element's lifetime and stops when the element leaves the tree. A 60/120 fps animation marks one scope dirty per frame, not the whole widget.

15. The widget catalog

Flutter-faithful names. Single-value leaves are tuple structs (positional construction); multi-prop widgets are record structs (struct-literal construction). v1 target set:

GroupWidgets
Layout — single childContainer, Padding, Center, Align, SizedBox, Expanded, Opacity, Transform, ClipRRect

Layout is Flutter's own constraint protocol (chapter 27 §2: layout(Constraints): Size, constraints down / sizes up), not a Flexbox/Yoga engine. Row/Column/Flex/Expanded reimplement the useful flex semantics natively, so layout stays single-pass, integrates with Skia text measurement and intrinsics, composes with the relayout-boundary hook, and adds no parallel layout tree or per-node FFI crossing. FutureBuilder/StreamBuilder integrate with the language's Future/async iterators (chapter 21): completion marks the builder's scope dirty.

17. End-to-end example

The macro form (the manual equivalent is §4):

import { App, Component } from "std:ui";
import { Column, Row, Text, Button, Center } from "std:ui";

@Component
function Counter(start: i64) {
  var count = state(start)
  Center {
    Column {
      Text("count: ${count}")                       // re-runs on count change
      Row {
        Button { label: "-", on_tap: () => { count = count - 1 } }   // independent scopes
        Button { label: "+", on_tap: () => { count = count + 1 } }
      }
    }
  }
}

function main() {
  App.run(Counter { start: 0 });   // opens the window (ch. 27 §6), mounts the tree, drives frames
}

Tapping + writes count; only the Text scope re-runs; the engine repaints only the changed paragraph's region; the two Buttons and the layout are never revisited.

18. Implementation & staging

  1. Widget/Element core + manual form. the Widget and Element interfaces, create_element, mount/update/unmount, reconciler + keys — all hand-written, no macro. Tests: reconcile insert/remove/reorder/keyed-move, identity preservation, unmount drops render objects.
  2. Reactive cells. Cell<T>, ctx.state, scope subscription, dirty marking; whole-build first, then scope splitting. Tests: write marks only dependent scopes, sibling isolation, soundness through helpers, rebuild_all opt-out.
  3. @Component macro. config struct + @Derive(Eq, Hash) + defaults(), content-block collection, state() read/write rewrite, scope boundaries, const hoisting. Tests: macro output equals the hand-written manual form (golden), call-site struct literal, equality skips unchanged subtree.
  4. BuildContext + Inherited. watch/read, scope-granular inherited subscriptions, escaped-context rejection. Tests: only watchers re-run, read doesn't subscribe, escape rejected.
  5. Effects, derived, remember. on_mount/launched/effect, cancel-on-leave, computed cells. Tests: ordering, cleanup before re-run + on unmount, derived recompute, task cancelled on leave.
  6. Gestures + hit testing. pointer-event union, hit path, arena. Tests: routing via match, tap/pan disambiguation.
  7. Animation. ticker on vsync, controllers → cells. Tests: one-scope-per-frame dirtying, controller stops on leave.
  8. Catalog + Material. §15 widgets, native flex layout, std:ui/material. Tests: layout golden cases, golden-image per widget (ch. 27 FakeCanvas + Skia native parity).

Per CLAUDE.md: unit + integration + e2e at every stage, including failure cases (escaped context, missing key causing state loss) and golden-image regression. Stages 1–6 test against the FakeCanvas with no GPU (chapter 27 §9). The macro stage's defining test is that its expansion is the manual form.

19. Open design decisions

  1. Cell access surface. Manual uses .get()/.set()/.update(); the macro rewrites x→x.get() and x = e→x.set(e). Confirm this rewrite vs. always-explicit cells even under the macro.
  2. Scope-boundary granularity. Split at every child, or only at explicit boundaries / list items? Proposed: child-boundary default, coarsen tiny scopes.
  3. Optional-prop ergonomics. { ..Container.defaults(), … } is the consistent idiom for optional props; confirm whether the catalog should also expose positional static constructors (SizedBox.square(80.0)) for the common leaves.
  4. Coarse vs fine default. Confirmed fine-grained default with a coarse opt-out (§6.3).
  5. Routing/navigation — a Navigator/router is its own design; deferred to a later chapter.

20. Summary

  • A widget is a plain struct that extends the single Widget interface; the value types Widget/Element/RenderObject are interface objects, written as the bare interface name (§3).
  • Two authoring forms, one runtime: a fully explicit manual form (§4, just struct + extend) and an optional @Component macro (§5) that expands to it for Compose-style brevity.
  • State is a remembered Cell<T> from ctx.state (§6); a write re-runs only the scopes that called get() — surgical recomposition, sound because tracking is by observed reads.
  • Built entirely from Otter Fusion idioms (§3): extend T: I, static Type.method() constructors, tuple/record struct construction, unions + match for events, trailing-closure .map { it }, @Derive(Eq, Hash, Clone), null-returning handlers, no +=, struct-literal "named args".
  • Composable logic is first-class (§10): a custom hook is just a function taking BuildContext and calling other hooks (ctx.state/effect/derived); identity is positional in the manual form and lexical-call-site-keyed under @Component/@Hook.
  • Flutter-faithful catalog and behavior (§§8–15) on Flutter's own constraint layout — no Flexbox/Yoga; every optimization lowers onto a chapter-27 §12 engine hook (§16); native-resource disposal is free from @RefCounted (§8).
