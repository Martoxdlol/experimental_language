27. UI Framework — Engine & Skia Integration design

A retained-mode, declarative UI framework in the spirit of Flutter, built on Otter Fusion's own runtime. This chapter specifies the bottom half: the Skia rendering engine, the native embedder (window, GPU surface, input), the threading and frame-scheduling model, and the resource-lifetime discipline that ties native objects to the language's GC. The top half — the user-level Widget/Element/State API and the reactive rebuild model — is deferred to chapter 28, but the optimization substrate it will stand on (repaint/relayout boundaries, damage tracking, compile-time dependency capture via procedural macros) is specified here in §13 because it is an engine concern.

Status — design, not yet implemented. This chapter specifies a framework that does not exist yet. The substrate it builds on is real: the FFI is complete (chapter 19 — extern struct/extern function, @CallConv, function-pointer callbacks, safepoints & trampolines), the GC supports opt-in deterministic finalization (@RefCounted, chapter 16 §8), the async runtime has a reactor/timer and (in progress) an M:N work-stealing executor (chapters 20–21), and the embedding engine (chapter 26) already demonstrates per-isolate hosting for hot reload. Everything above the embedder is portable Otter Fusion. The single hard external dependency is Skia, reached the way Flutter reaches it — through a co-designed native shim, not a generic FFI. §15 records what exists today versus what is new work.

1. Scope, goals & non-goals

The framework targets the same problem Flutter targets: a single declarative, reactive UI codebase that renders its own pixels through a GPU-accelerated 2-D engine, rather than wrapping native platform widgets. Rendering its own pixels is what makes the framework portable and what makes Skia the load-bearing dependency.

This chapter's goals.

  • Specify how Otter Fusion talks to Skia — the C shim ABI, the FFI binding layer, and how native handles are owned and freed.
  • Specify the embedder: window/GPU-surface creation and the input/lifecycle event path from the platform into the language's async runtime.
  • Specify the threading model and how it cooperates with the GC's world-barrier stop-the-world (chapter 16).
  • Specify the frame pipeline (build → layout → paint → composite → rasterize) as a sequence of retained, recorded artifacts — never per-primitive FFI calls on the hot path.
  • Specify the engine-level optimization substrate (§13) that the reactive layer and procedural macros will exploit to minimize rebuilds, relayouts and repaints.

Non-goals for this chapter (deferred to chapter 28): the public Widget type hierarchy, State/setState, the element reconciliation algorithm, gesture recognition, and the Material/Cupertino-style component library. They are named here only where the engine must expose a hook for them.

Out of scope entirely (for now): accessibility tree bridging, platform-native embedded views (texture/platform-view composition), and a non-Skia backend. The architecture keeps the renderer behind a Canvas interface (§9) so a second backend (a future Impeller-style renderer, or a software rasterizer) remains possible, but only Skia is specified.

3. The engine boundary — the Flutter lesson

Flutter does not reach Skia through Dart's public FFI (dart:ffi, which exists for app/plugin authors calling third-party C libraries). The framework↔engine boundary is the Dart VM's privileged native-hooks mechanism (the tonic library + @pragma('vm:external-name')): C++ functions registered into the isolate that receive Dart_Handles and can touch the Dart heap directly. Three design choices make that boundary cheap, and all three are independent of the binding mechanism — so Otter Fusion adopts them while reaching Skia through an ordinary (but co-designed) C shim:

  1. Record, don't call. Canvas.drawRect(…) issues no GPU call; it appends to a display list that lives native-side. A frame crosses the ABI a handful of times, not once per primitive (§9).
  2. Thin peers, deterministic free. Heavy objects (surfaces, pictures, paragraphs, images) live in C/Skia; the language holds small handle objects whose destructor unrefs the native peer. Flutter does this with tonic's weak-persistent-handle finalizers; Otter Fusion does it with @RefCounted + Drop (§11), which is a closer, deterministic match.
  3. Rasterize off the build thread. The thread that builds the frame never calls the GPU. It produces a layer tree that a dedicated raster thread consumes (§7).
Why a shim and not direct FFI to Skia. Skia's real API is C++, which cannot cross the C ABI that chapter 19 speaks. libofskia is a thin extern "C" wrapper over exactly the Skia surface we use — the same pattern Flutter's engine uses internally. The shim is compiled separately and linked into the built program through the system-linker path build already uses. The one capability Flutter's native hooks have that a C shim lacks — touching the managed heap directly — we deliberately forgo: peers are opaque handles and payloads cross by value, exactly the boundary discipline std:engine's @Bridge already enforces (chapter 26 §5).

The practical consequence of using top-level extern symbols (chapter 19 §8: closures cannot cross the C ABI) is that callbacks into the language — vsync, input, lifecycle — are a fixed, small set of top-level extern functions, not a callback per widget. This is identical to how Flutter exposes a handful of entry points on PlatformDispatcher and is what §6 specifies.

4. The C shim — libofskia

libofskia is a hand-written C façade (implemented in C++ against Skia, exported extern "C") that exposes only the operations the engine needs. Keeping the surface small is deliberate: it is the entire trusted, unsafe boundary, and every symbol in it is one the FFI binding layer must declare and the test suite must exercise. The shim owns no policy — it is a mechanical 1:1 wrapper. Its surface groups into six families:

FamilyRepresentative symbolsPurpose
Contextofsk_context_make_gl, ofsk_context_releaseGPU backend context bound to the embedder's GL/Metal/Vulkan handle
Surfaceofsk_surface_make_render_target, ofsk_surface_get_canvas, ofsk_surface_flushthe on-screen render target and its canvas
Recorderofsk_recorder_begin, ofsk_recorder_finish → SkPicture*record draw ops into a display list (a Picture)
Canvas opsofsk_canvas_draw_rect, _draw_rrect, _draw_path, _draw_picture, _draw_paragraph, _clip_rrect, _save_layer, _restore, _concatthe recordable primitive set
Paragraphofsk_para_build, ofsk_para_layout, ofsk_para_metricstext shaping & layout (§10)

Every constructor returns an opaque handle (typedef struct OfSkSurface OfSkSurface; … → OfSkSurface*) and every handle family has a single _release/_unref entry. The shim never calls back into Otter Fusion (the input direction is the embedder's job, §6), so it has no dependency on the language runtime and can be unit-tested in C on its own.

The shim is the only place C++ exceptions / Skia aborts can originate. Each entry is wrapped so a Skia failure returns a null handle or an error enum, never unwinds across the C ABI into Cranelift frames (which, per the worker-panic-isolation work in goals.txt, cannot be unwound through). Error enums surface in the language as ordinary union returns.

5. The FFI binding layer — std:ui/skia

std:ui/skia is pure binding: one extern function per shim symbol, extern structs for the POD parameter/return layouts (rects, colors, paint params, transform matrices), and a managed handle type per Skia object family. Nothing above this module sees a raw pointer.

// std:ui/skia — illustrative (design)
import { Foreign } from "core:ffi";

// POD layouts cross by value as extern structs (chapter 19).
extern struct OfRect  { left: f32, top: f32, right: f32, bottom: f32 }
extern struct OfColor { r: f32, g: f32, b: f32, a: f32 }
extern struct OfXform { a: f32, b: f32, c: f32, d: f32, e: f32, f: f32 }   // 2-D affine

// Opaque native handles are imported as opaque foreign pointer types.
extern type OfSkSurface;
extern type OfSkCanvas;
extern type OfSkPicture;
extern type OfSkPaint;

@CallConv("c") extern function ofsk_surface_get_canvas(s: *OfSkSurface): *OfSkCanvas;
@CallConv("c") extern function ofsk_canvas_draw_rect(c: *OfSkCanvas, r: *OfRect, p: *OfSkPaint);
@CallConv("c") extern function ofsk_recorder_finish(rec: *OfSkRecorder): *OfSkPicture;
@CallConv("c") extern function ofsk_picture_release(p: *OfSkPicture);

Above the raw externs sits a thin handle layer that gives every native object a managed owner with a deterministic destructor (§11):

// A managed owner for a native SkPicture. Dropping it unrefs the peer — Flutter's
// tonic peer-finalizer pattern, but deterministic via @RefCounted (chapter 16 §8).
@RefCounted
struct Picture { raw: *OfSkPicture }

extend Picture: Drop {
  function drop(self) { ofsk_picture_release(self.raw); }
}

6. The embedder — window, surface & input

Skia rasterizes; it does not create windows or deliver input. The embedder (std:ui/embedder, also over libofskia which bundles GLFW or SDL) owns: a platform window, the GPU context Skia draws into, and the event source. It is the only component that crosses the boundary inbound (platform → language), and per §3 it does so through a fixed set of top-level extern function entry points, not closures.

The inbound entry points

The shim drives a native event loop on the platform thread and invokes registered C function pointers. On the language side these are top-level extern functions (chapter 19 §8). Each recovers the engine instance from a *c_void user-data pointer — the conventional C-callback state pattern — pinned for the lifetime of the window via the scoped-pin facility (chapter 19 §8, "passing managed state into a callback"):

// Top-level extern entry points — the entire inbound surface.
@CallConv("c") extern function of_on_begin_frame(user: *c_void, nanos: u64) {
  var engine = Engine.from_user(user);   // recover pinned engine handle
  engine.request_frame(nanos);            // post into the executor; returns fast
}

@CallConv("c") extern function of_on_pointer_packet(user: *c_void, buf: *u8, len: usize) {
  var engine = Engine.from_user(user);
  engine.enqueue_pointer_packet(buf, len);  // decode a *batch*, not one event
}

@CallConv("c") extern function of_on_window_metrics(user: *c_void, w: u32, h: u32, dpr: f32) {
  Engine.from_user(user).set_metrics(w, h, dpr);
}
Batched, serialized input — the PointerDataPacket idea. Pointer/touch events arrive as a packed byte buffer of many events, decoded once on the language side, exactly like Flutter's PointerDataPacket. This keeps boundary crossings rare (one per frame's worth of input, not one per move event) and keeps the hot path off the FFI layer.

Each inbound entry point does the minimum — recover the engine, hand the data to the runtime, return immediately. The real work happens on the executor, decoupled from the platform thread (§7). This is the inverse of the outbound rule: outbound (drawing) is recorded and flushed once per frame; inbound (events) is captured and posted once per batch.

7. The threading model & GC safepoints

Following Flutter, the engine separates concerns across threads. Otter Fusion maps them onto the async runtime (chapters 20–21) and must reconcile them with the GC's world-barrier stop-the-world (chapter 16): every thread that touches managed memory is a mutator that must gate at a safepoint when the collector stops the world.

RoleFlutter nameOtter Fusion realization
Platform / eventPlatform threadthe OS thread libofskia's native loop runs on; only marshals events inbound via §6
Build / layout / paintUI threadthe async executor (the M:N work-stealing pool, in-progress goal); build/layout/paint run as tasks here
RasterizeRaster threada dedicated thread that owns the GPU context and is the only caller of ofsk_surface_flush / GPU-touching shim ops
The pinned-GPU-thread constraint. A GPU context (GL/Metal/Vulkan) is affine to the thread that created it; Skia must be flushed from that thread. So build and layout may run as ordinary executor tasks, but the layer-tree flush is marshalled to the raster thread, which holds the context. The raster thread is a GC mutator: it registers as a safepoint-gating thread and parks at a safepoint during a world-stop, identical to how Thread.spawn workers already participate in the world barrier. A frame must never be left half-flushed across a world-stop — the flush is a single safepoint-bounded region.

The frame clock is the executor's reactor/timer: the platform vsync signal (of_on_begin_frame) wakes a frame task rather than blocking any thread. There is no user-visible block_on anywhere in the loop — consistent with the async design (chapter 21).

8. The frame pipeline

A frame is a fixed sequence of phases. Phases 1–4 run on the executor (UI role); phase 5 is marshalled to the raster thread. Each phase consumes the previous phase's retained output, and — crucially for §13 — each phase is allowed to skip subtrees that are known-clean.

  vsync ──► 1. BUILD     dirty Elements rebuild → updated RenderObject tree   (ch. 28 hook)
            2. LAYOUT    walk dirty RenderObjects: layout(Constraints)→Size
            3. PAINT     walk repaint-dirty RenderObjects → record display lists
            4. COMPOSITE assemble the layer tree (SceneBuilder)
            ──────────────────────────────── marshal to raster thread ──────
            5. RASTER    compositor replays layers → Skia → GPU surface flush
The five frame phases. Phases 1–4 are pure Otter Fusion on the executor; phase 5 owns the GPU context.

The pipeline owner (std:ui/engine) holds the three persistent trees (element, render, layer) and the dirty sets. A frame is requested by marking a node dirty and calling request_frame; multiple marks coalesce into one frame. This is the standard Flutter build owner / pipeline owner split, and it is the seam where the optimization substrate (§13) lives: the dirty sets decide what each phase may skip.

9. Recording canvas, pictures & the layer tree

The paint phase does not draw to the screen. It draws to a recording canvas whose operations are captured into a Picture (a native SkPicture display list, §5). The renderer only ever sees a Canvas interface:

interface Canvas {
  function draw_rect(self, r: Rect, p: Paint);
  function draw_rrect(self, r: RRect, p: Paint);
  function draw_path(self, path: Path, p: Paint);
  function draw_paragraph(self, par: Paragraph, at: Offset);
  function draw_picture(self, pic: Picture);        // replay a cached sub-list
  function save_layer(self, bounds: Rect, p: Paint);
  function clip_rrect(self, r: RRect);
  function transform(self, m: Xform);
  function restore(self);
}

Two implementations exist: SkiaCanvas (forwards each op to the shim's recorder) and RecordingCanvas/FakeCanvas for tests, which records ops into an in-memory list the test suite can assert against without any native dependency. Because the renderer is written against the interface, the entire rendering and layout layer (§2) is testable with zero Skia linked — important for the project's test-density bar.

The layer tree

The composite phase assembles a layer tree: a tree of composited layers (transform, clip, opacity, offset, and picture leaves) that the raster thread replays. Layers are the unit of retention across frames: a layer backed by a clean subtree is reused verbatim, so an unchanged subtree costs nothing to repaint. This is the engine-level mechanism behind "reduce re-renderings" (§13). The layer tree is the only artifact handed across the thread boundary to the raster thread; it is immutable once handed off.

10. Text shaping & SkParagraph

Text is the single hardest 2-D problem (shaping, bidi, font fallback, line breaking) and the strongest reason to choose Skia over a hand-rolled rasterizer. The framework leans entirely on Skia's SkParagraph/SkShaper through the shim's paragraph family (§4): a ParagraphBuilder takes styled text runs, produces a Paragraph handle, layout(maxWidth) shapes it, and draw_paragraph records it onto a canvas.

A laid-out Paragraph is a @RefCounted handle over the native paragraph (§11). Because shaping is expensive, a paragraph whose text/style/width are unchanged is cached on its render object across frames — a concrete instance of the memoization the optimization substrate generalizes (§13).

11. Lifetime — peers, @RefCounted & the GC backstop

Every native Skia object (surface, picture, paragraph, paint, path, image) is owned by a managed @RefCounted handle whose drop calls the matching shim _release. This is precisely Flutter's tonic peer pattern — a lightweight managed object fronting a heavy native peer — but with two improvements the language gives for free:

  • Deterministic release. @RefCounted drop runs the instant the last strong reference goes away (chapter 16 §8), not at the next GC. Native GPU resources — which are scarce and whose lifetime matters — are freed promptly, the way dispose() works in Flutter, without a manual dispose() call.
  • Cycle safety. The element/render/layer trees have parent↔child back references (cycles). Reference counting alone leaks cycles; the tracing GC is retained as the cycle-collector backstop (chapter 16 §8), so the framework can hold natural bidirectional links without leaking.

The rule: native handles are deterministic (@RefCounted); pure-language tree nodes are ordinary managed objects (GC-traced). This mirrors Flutter's split between engine-owned C++ objects and framework Dart objects, and it means the scarce, expensive resources get prompt release while the cheap, cyclic graph gets the convenience of tracing GC.

12. The optimization substrate (language leverage)

This is where the framework departs from a literal Flutter port. Flutter's rebuild minimization is largely runtime and convention (const constructors, manual RepaintBoundarys, const widgets, the shouldRebuild hand-written checks). Otter Fusion can push much of this to compile time using procedural macros (chapter 22, which run before type-checking and are hygienic) and the type system. The user-level API that exposes these is chapter 28; the engine hooks they target are specified here.

12.2 Compile-time dependency capture (the differentiator)

Flutter rebuilds a widget when setState is called or an InheritedWidget it depends on changes; the dependency set is discovered at runtime (dependOnInheritedWidgetOfExactType) and the rebuild rebuilds the whole build() method. Otter Fusion can do better at two levels, both built on language features that already exist:

  • Macro-derived dependency tracking. A @Component procedural macro can analyze a component's build body at compile time and emit, per reactive field it reads, the exact set of sub-expressions that depend on it — turning a coarse "rebuild on any change" into "recompute only the dependent fragments." Because macros run pre-resolve and are hygienic (chapter 22), the generated dependency graph is sound and invisible to the user. This is the "smarter dependency change detection" goal made structural rather than runtime-heuristic.
  • Compile-time const subtrees. A subtree the macro proves is built only from compile-time-constant inputs is hoisted to a single cached widget/layer allocated once — the automatic generalization of Flutter's manual const widgets. The macro can detect constness from the resolved HIR (the typed tree, per the README architecture) rather than relying on the author to write const.
  • Value-identity diffing. Immutable widget config structs get a derived structural-equality + content-hash (a @Derive-style macro, chapter 22) so the reconciler can skip an Element subtree when the new widget config is bit-for-bit equal to the old — cheaper and more reliable than Flutter's operator== convention because it is generated, total, and cannot be forgotten.
The principle. Everything Flutter asks the developer to remember — mark a RepaintBoundary, write const, implement operator==, call dispose() — Otter Fusion derives or enforces: repaint/relayout boundaries from layout properties, constness from the HIR, equality from a derive macro, and disposal from @RefCounted drop. Correctness moves from convention to the compiler.

None of §12.2 changes the engine contract; it changes what marks nodes dirty and how narrowly. The engine exposes the dirty sets and boundary flags (§12.1); the macros and reactive layer (chapter 28) decide how precisely to set them.

13. Hot reload via isolates

The embedding engine (chapter 26) hosts guest Otter Fusion in a sandboxed isolate with its own heap and GC, selected by a thread-local current-isolate pointer. This is a natural hot-reload substrate: run the application's widget code as the guest, keep the embedder, GPU context, and persistent trees in the host, and reload the guest's compiled artifact on source change while preserving host-side State across the swap (Flutter's hot-reload contract). The bridge ABI (@Bridge, chapter 26 §5) already defines how data crosses the host/guest boundary by value, which matches the widget-config model (immutable, copyable). This is a chapter-28-and-later capability noted here because the engine must be designed isolate-aware from the start (the pipeline owner lives host-side; the build callback calls into the guest).

Linking

libofskia (Skia + text + windowing + GPU bindings) is a prebuilt native artifact per target triple. A program importing std:ui links it through the same system-linker step build uses for run/build (the runtime already links native libc and FFI targets, chapter 19). run (JIT) loads it as a shared library; build links the static or dynamic archive. The GPU backend is selected per platform: GL/ANGLE on Linux/Windows, Metal on macOS/iOS, Vulkan where available — all behind the context family in the shim (§4), invisible above std:ui/skia.

Bundling — decided. libofskia ships with the toolchain, making std:ui a true standard module (Flutter-SDK style). The native blob is part of the per-target distribution; no package fetch is required to build a UI program.

15. Implementation & staging

What exists today (the substrate)

  • FFI: extern struct/function, @CallConv, function-pointer callbacks, scoped pin for managed callback state, safepoints & trampolines (chapter 19).
  • Deterministic finalization: @RefCounted + Drop with the tracing GC as cycle backstop (chapter 16 §8).
  • Async runtime with reactor/timer; M:N work-stealing executor in progress (chapters 20–21, goals.txt).
  • World-barrier STW GC with safepoint gating for worker threads (chapter 16).
  • Procedural macros, hygienic, pre-resolve (chapter 22) — for §12.2.
  • Per-isolate hosting + bridge ABI (chapter 26) — for §13.

New work, staged (each stage shippable & test-gated)

  1. Shim + bindings. Write libofskia (context/surface/canvas families) and std:ui/skia; prove a window opens, a rect paints, the surface flushes. Tests: C-side shim unit tests; FFI round-trip tests; a golden-image smoke test.
  2. Embedder + event loop. Window metrics, vsync → frame request, batched pointer packets into the reactor (§6). Tests: synthetic packet decode, vsync-drives-frame, no block_on on the loop.
  3. Recording canvas + layer tree. The Canvas interface, the FakeCanvas, picture recording, layer assembly, raster-thread flush (§8–9). Tests: FakeCanvas op assertions, layer reuse, cross-thread flush + GC-stress.
  4. Render layer. RenderObject, constraints/layout/paint, a box/flex/stack/padding set, relayout & repaint boundaries (§12.1). Tests: layout golden cases, boundary-stops-propagation, paint-skips-clean-subtree.
  5. Text. Paragraph build/layout/draw + caching (§10). Tests: shaping golden images, paragraph-cache-hit on unchanged inputs.
  6. (Chapter 28) Widgets, reconciliation, reactive layer, macros — builds on this chapter's engine; the §12.2 optimizations land with it.

Per the project's bar (CLAUDE.md): every stage carries unit + integration + e2e tests, including failure and "should-not-work-but-does" cases; the renderer's interface-against-FakeCanvas design means most of the framework is testable without a GPU, and the Skia-backed path adds golden-image and native-parity tests on top.

16. Open design decisions

These are genuine language/distribution decisions that need a call before implementation (per CLAUDE.md — ask before big design changes):

  1. Module scheme. decided The framework is std:ui — a standard module bundled with the toolchain (Flutter-SDK style, native libofskia shipped with the distribution). The submodules follow: std:ui/skia, std:ui/embedder, std:ui/engine, std:ui/render, std:ui/material.
  2. Windowing dependency. GLFW vs SDL2 inside libofskia. SDL2 brings audio/gamepad/mobile breadth; GLFW is leaner and desktop-focused. Affects mobile reach.
  3. GPU backend matrix. Which of GL/Metal/Vulkan to support at v1, and whether to require ANGLE for a uniform GL path on desktop.
  4. Skia vs a future Impeller-style renderer. Committing the Canvas interface (§9) now keeps a second backend possible; do we want to reserve that seam explicitly or hard-commit to Skia?
  5. Hot-reload via isolates (§13). Whether to design the pipeline owner isolate-aware from day one (recommended) or add it later (cheaper now, costlier to retrofit).

17. Summary

  • The framework is five layers (§2); the top two (widgets, components) are chapter 28, the bottom three (render, engine, skia/embedder) are this chapter.
  • Skia is reached through a co-designed C shim (libofskia, §4) and a pure FFI binding layer (std:ui/skia, §5) — the same shape Flutter uses, since the framework↔engine boundary is privileged native code, not generic FFI (§3).
  • The boundary is cheap because of three borrowed tricks: record don't call (display lists, §9), thin peers with deterministic free (@RefCounted, §11), and rasterize off the build thread (raster thread + GC safepoints, §7).
  • Inbound events are a small fixed set of top-level extern entry points with batched, serialized payloads (§6) — closures never cross the C ABI.
  • The frame pipeline (§8) produces retained artifacts each phase can skip; the dirty sets and boundaries (§12.1) are the engine's optimization hooks.
  • The differentiator (§12.2): procedural macros + the typed HIR push Flutter's remember-to-optimize conventions (const widgets, RepaintBoundary, operator==, dispose) into compile-time-derived, enforced behavior — finer-grained rebuild, derived structural equality, automatic const subtrees, deterministic disposal.
  • Open decisions (§16) — module scheme/bundling, windowing lib, GPU matrix, backend seam, isolate-aware hot reload — need a call before implementation.
