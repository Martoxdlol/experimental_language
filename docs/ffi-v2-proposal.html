FFI v2 — Proposal

A re-shape of the Foreign Function Interface that adds the smallest possible amount of new syntax, and instead does the heavy lifting through new core types, decorators on existing item shapes, manifest entries, and tooling.

Design constraint: avoid new syntax where stdlib and decorators can do the job. The only new syntax in this proposal is:

  • &expr — address-of operator.
  • *ptr — pointer dereference (prefix) and (*ptr).field field access.
  • [T; N] — fixed-size array type, valid only inside extern struct fields and extern function signatures.
  • extern type T — opaque foreign type declaration (extends the existing extern keyword family).
  • extern var name: T — foreign global declaration (extends the existing extern keyword family).
  • as extends to pointer-to-pointer reinterpretation.

Nothing else is new keyword/operator/block syntax. No unsafe block, no defer, no union keyword, no const keyword, no field-level decorators, no trailing-lambda call syntax, no @Repr(C) on regular structs. extern struct stays as the C-layout form, exactly as it is today.

1. Pointers — *T, &expr, *ptr

*T already exists in the current spec as a type form. This proposal adds two operators:

1.1 &expr — address-of SYNTAX

extern function getrusage(who: i32, out: *Rusage): i32

function snapshot(): Rusage | i32 {
  var ru = Rusage { ... }
  var rc = getrusage(0i32, &ru)
  if rc != 0i32 { return rc }
  ru
}

&expr produces a *T from a value of type T. Restrictions:

  • The expression must be a place-expression (a local variable, struct field, or array element) — not a temporary.
  • If the operand lives on the managed heap, & auto-pins for the duration of the enclosing extern call and auto-unpins on return. This is the only implicit pin in the language.
  • If the operand is an extern struct on the stack (the common case), no pin is needed.
  • The resulting pointer cannot be stored in a longer-lived location than the call site. Returning it, capturing it in a closure, or assigning it to a struct field is a compile error.

1.2 *ptr — dereference SYNTAX

var p: *Counter = ...
var n = (*p).value           // read
(*p).value = (*p).value + 1  // write

*ptr is a prefix operator on a pointer value. Combined with field access, (*ptr).field reads/writes through the pointer. Rules:

  • Dereferencing a *T | null whose value is null panics with null pointer dereference.
  • Dereferencing a pointer to a managed-heap object that is not currently pinned is undefined behavior.
  • The language does not introduce an unsafe block. Holding a *T is the marker. If you wrote *T in your code, you've left the language's safety guarantees and the responsibility is yours.

1.3 as on pointers SYNTAX

as already covers union narrowing, primitive conversion, and interface widening/narrowing. This proposal extends it to pointer-to-pointer reinterpretation:

var p: *c_void = ...
var q: *MyStruct = p as *MyStruct    // no-op at runtime; type reinterpretation

Both source and destination must be pointer types. The cast is a no-op at runtime — the user vouches for the layout. No other as behavior changes.

1.4 Nullable pointers — *T | null

Unchanged. *T | null lays out as a single word, with null represented as 0x0. This is the existing rule, generalized: any union null | P where P's representation cannot legitimately be all-zero qualifies for null-pointer optimization. Applies to *T, extern function pointers, and extern type opaque handles.

2. Layout decorators on extern struct

extern struct stays as the C-layout opt-in (no GC header, foreign heap or stack). Four decorators cover everything else; each is a compiler-known proc-macro, blessed the same way @Derive is in 22-macros.md §22.11. All sit at the item level, exactly where 22-macros.md §22.2 already permits decorators.

@Packed(1)
extern struct DiskHeader {
  pub magic:   u32,
  pub version: u16,
  pub flags:   u8,
}

@Align(64)
extern struct CacheLine {
  pub bytes: [u8; 64],
}

@Transparent
struct Handle(i32)

@Union
extern struct FloatBits {
  pub f: f32,
  pub i: u32,
}
DecoratorEffect
@Packed(N) SYNTAXFields not aligned beyond N bytes. @Packed alone means packing 1.
@Align(N) SYNTAXMinimum alignment N on the struct.
@Transparent SYNTAXApplied to a tuple struct with exactly one non-zero-sized field. The wrapper has the same ABI as the inner type, including NPO. Works on regular and extern structs.
@Union SYNTAXApplied only to extern struct. All fields share offset 0; size is the max field size; reads return whatever bits are there. The user is responsible for tracking which field is "active."

What's not added: @Repr(C), @Repr(Lang), @Bitfield, @FlexArray. extern struct already conveys "C layout, no GC header"; a separate @Repr would be redundant. Bitfields and flexible array members are handled by stdlib idioms (§5.4, §5.5) — no field-level decorators are needed.

2.1 C enums — no special construct

A C enum is an integer with named constants. Express it as a type alias plus module-level values:

pub type FileMode = i32

pub var MODE_READ:  FileMode = 0i32
pub var MODE_WRITE: FileMode = 1i32
pub var MODE_RW:    FileMode = 2i32

If exhaustive matching matters, write a language-side discriminated union on top and translate at the boundary:

pub type ParsedMode = Read | Write | ReadWrite | UnknownMode

function parse(m: FileMode): ParsedMode {
  if m == MODE_READ  { Read }
  else if m == MODE_WRITE { Write }
  else if m == MODE_RW    { ReadWrite }
  else { UnknownMode }
}

No new syntax for C enums; bindgen (§12) emits this pattern automatically.

3. extern type and fixed-size arrays

3.1 Opaque foreign types — extern type SYNTAX

extern type Sqlite3
extern type Sqlite3Stmt

extern function sqlite3_open(path: *u8, db: **Sqlite3): i32
extern function sqlite3_prepare_v2(
  db: *Sqlite3, sql: *u8, n: i32, stmt: **Sqlite3Stmt, tail: **u8,
): i32

An extern type T is a foreign-only nominal type with unknown size and alignment. Values of type T cannot be constructed, copied, or destructured in this language; only *T and *T | null are usable forms. Pattern matches the FILE*, sqlite3* idiom in C.

3.2 Fixed-size arrays — [T; N] SYNTAX

extern struct InAddr {
  pub bytes: [u8; 4],
}

extern struct Sockaddr {
  pub family: u16,
  pub data:   [u8; 14],
}

extern function read_into(buf: *[u8; 256], n: usize): isize

[T; N] is a fixed-size array, N resolved at compile time, T any extern-compatible type. Scope of the type form is narrow:

  • Allowed as an extern struct field type.
  • Allowed as an extern function parameter or return type (typically via *[T; N]).
  • Not allowed in regular language types (no var x: [i32; 4] at function-local positions outside extern contexts).

This is the minimum addition that lets extern structs mirror C structs without bringing const-generics or a general array type into the language.

4. C-width aliases — core:ffi STDLIB

import {
  c_int, c_uint, c_long, c_ulong, c_longlong, c_ulonglong,
  c_short, c_ushort, c_char, c_schar, c_uchar,
  c_float, c_double,
  c_size_t, c_ptrdiff_t, c_intptr_t, c_uintptr_t,
  c_void, c_va_list,
} from "core:ffi"

Widths are resolved at compile time per target.

  • Numeric aliases (c_int, c_long, etc.) lower to the appropriate fixed-width type for the target ABI.
  • c_void is declared as extern type c_void — opaque, no value form. Only *c_void is usable.
  • c_va_list is declared as extern type c_va_list — for wrapping variadic libc functions via the va_list interface.

core:ffi is part of core:, so freestanding targets get it without an OS.

5. Foreign allocation — Foreign STDLIB

Foreign is a namespace struct with the foreign-heap allocator API:

pub struct Foreign;

extend Foreign {
  function alloc<T>():                                  *T | null
  function alloc_zeroed<T>():                           *T | null
  function alloc_flex<T, E>(extra_count: usize):        *T | null
  function realloc<T>(p: *T, new_size: usize):          *T | null
  function free<T>(p: *T)
}

All methods are static (no self parameter — see 10-interfaces.md §10.1). All return null on failure; foreign allocation is fallible, unlike managed allocation.

Buffer.alloc(size) (already in core:prelude) is reimplemented on top of Foreign.alloc; no behavior change for existing code.

5.1 Flexible array members

The C idiom struct foo { int n; char data[]; } is expressed by declaring the trailing pointer field as a regular pointer and using alloc_flex to obtain a single allocation:

extern struct Message {
  pub kind:   u32,
  pub length: u32,
  pub data:   *u8,        // points into the same allocation
}

function make_message(kind: u32, payload: List<u8>): *Message | null {
  var p = Foreign.alloc_flex<Message, u8>(payload.size() as usize)
  if p is null { return null }
  // initialize header; copy payload bytes after the header; set data pointer
  ...
  p
}

No @FlexArray decorator and no new field marker. The allocator helper is the only addition.

5.2 Bitfields

Not directly supported. C bitfield layouts are platform-dependent and rarely used in interop. Treat the underlying integer as a regular field and mask/shift in user code:

extern struct Flags {
  pub raw: u32,
}

extend Flags {
  function kind(self):   u32 { self.raw & 0x07u32 }
  function dirty(self):  bool { (self.raw & 0x08u32) != 0u32 }
  function serial(self): u32 { (self.raw >> 4) }
}

If a C library forces bitfield interop, bindgen (§12) emits the accessor methods above and warns that the underlying layout is platform-dependent.

6. Strings — CStr, CString STDLIB

str is not C-compatible (managed-heap, UTF-8 with a length header, not NUL-terminated). core:ffi ships two boundary types.

extern struct CStr {
  pub ptr: *u8,    // NUL-terminated UTF-8 byte sequence; lifetime unspecified
}

pub struct CString { ... }   // owned NUL-terminated foreign-heap buffer

Buffer (already in core:prelude) covers the (ptr, size) case when length matters separately. Both CStr and Buffer are extern structs, so they pass to C by value with no shim.

7. Extern functions and decorators

extern function stays as it is (import without body / export with body). Six decorators compose on top, all top-level item decorators in the existing macro system:

@Link(lib = "z", kind = "dynamic", version = ">=1.2")
@Symbol("inflateInit_")
extern function zlib_inflate_init(strm: *ZStream, ver: *u8, sz: i32): i32

@CallConv("system")
extern function WinMain(...): i32

@Variadic
extern function printf(fmt: *u8): c_int

@Reentrant("any")
@OnPanic("abort")
extern function on_tick(data: *c_void) {
  ...
}
DecoratorOnEffect
@Link(lib, kind, version?, path?) SYNTAXimportsReference to a [package.links] entry. If absent, symbol resolves from the host process.
@Symbol("name") SYNTAXimports & exportsOverride symbol name; default is the function name.
@CallConv("c" | "system" | "stdcall" | "fastcall") SYNTAXimports & exportsCalling convention. Default "c".

7.1 Calling a variadic import

import { c_int } from "core:ffi"

@Variadic
extern function printf(fmt: *u8): c_int

var fmt = (CString.from_str("%d + %d = %d\n") as CString).as_cstr()
printf(fmt.ptr, 1i32, 2i32, 3i32)

The compiler applies C default argument promotions to each variadic argument at the call site. The fixed prefix in the signature is checked normally.

7.2 Function pointers and callbacks

The function-type syntax extern (T1, T2) -> R already exists (09-functions.md §9.3). Closures cannot be passed as C function pointers — no environment slot. For callbacks with state, core:ffi provides a generic bundle:

extern struct Callback<C, R> {
  pub fn:   extern (*c_void, C) -> R,
  pub data: *c_void,
}

Many C APIs already accept (callback, userdata) as separate parameters — pass them separately. Callback<C, R> is for APIs that expect them bundled in a struct.

8. extern var and constants SYNTAX

@Link(lib = "c")
extern var errno: i32           // thread-local on most platforms; binding handles TLS

@Link(lib = "c")
extern var environ: **u8

// For build-time numeric constants from a header, the binding generator
// emits a module-level `pub var`:
pub var PATH_MAX: usize = 4096usize
  • extern var name: T declares a foreign global. Reads and writes are direct. The compiler emits the platform-appropriate load (TLS on thread-local symbols).
  • Constants from a C header are emitted as pub var values — no new const keyword is needed; module-level var initializers are already compile-time constants per 17-modules.md §17.6.

9. Pinning v2 — scoped and long-lived STDLIB

Today's manual pin/unpin is leak-prone. Replace with two complementary APIs in core:ffi.

9.1 Scoped pin — with_pin

import { with_pin } from "core:ffi"

with_pin(state, |ptr| {
  call_native_op(ptr)
})
pub function with_pin<T, R>(value: T, body: (*T) -> R): R
  • Pins value before invoking body.
  • Unpins on every exit path, including panic-unwind.
  • The pointer is valid only inside body; the compiler enforces this with the same rule that gates &expr (§1.1).

Closure passing is the existing in-paren form (09-functions.md §9.5) — no trailing-lambda syntax is introduced.

9.2 Long-lived pin — Pin.acquire and PinHandle<T>

import { Pin, PinHandle } from "core:ffi"

var handle = Pin.acquire(state)
register_callback(on_tick, handle.ptr() as *c_void)
// later...
unregister_callback(handle.ptr() as *c_void)
handle.release()
pub struct Pin;
extend Pin {
  function acquire<T>(value: T): PinHandle<T>
}

pub struct PinHandle<T> { ... }
extend<T> PinHandle<T> {
  function ptr(self):     *T
  function release(self): null
}
extend<T> PinHandle<T>: Drop {
  function drop(self) { /* releases if not already released */ }
}

PinHandle<T> implements Drop. If release() is never called, the handle's Drop impl releases the pin and (in debug builds) emits a warning. The resource is owned by the handle — there is no manual pin/unpin user-API anymore.

9.3 Auto-pin via &

&managed_local at an extern call site pins for the duration of that call only (§1.1). This is the most common pin pattern; with_pin is for cases where the foreign function uses the pointer for the lifetime of a closure body that does additional work, and Pin.acquire is for callback registrations that outlive any single call.

10. Runtime semantics

The previous spec was silent on threading, panics, and GC safe-points across the FFI boundary. Specify them.

10.1 Safe-points around imports

Every call to an imported extern function is compiled with a thread-blocked transition on either side:

  • Before the call: the thread's stack is snapshotted; the thread declares itself blocked. Other threads can run GC without waiting for this thread to reach a safe-point.
  • During the call: pinned values remain rooted. Nothing else on the calling thread's stack is reachable for tracing.
  • After the call: the thread re-acquires its mutator state. If GC ran during the call, the thread re-checks its roots.

This is the JNI / Cgo / .NET pinvoke model. It's not exposed at the source level; the compiler emits the transitions automatically. Long-running C calls do not stall the rest of the program.

10.2 Foreign threads calling exports

A thread the runtime did not spawn must attach before invoking an exported extern function. Two ways:

Manual

import { attach_thread, detach_thread } from "core:ffi"

extern function on_tick(data: *c_void) {
  attach_thread()
  do_work(data)
  detach_thread()
}

Automatic via @Reentrant("any")

@Reentrant("any")
extern function on_tick(data: *c_void) {
  do_work(data)
}
@Reentrant valueMeaning
"managed-only" (default)Only threads the runtime created may call this. Calling from an unattached thread panic-aborts in debug, is UB in release.
"any"Compiler emits attach/detach automatically. Safe to call from any thread; small per-call cost.

Attach behavior:

  • Registers the thread with the runtime so the GC can scan its stack.
  • Refcount operations on objects this thread touches become atomic (matches the cross-thread rule in 16-memory.md §16.4).
  • Detach removes the thread from the GC root set.

The manual form intentionally has no defer-style scope marker — that would require new syntax. Users who want lexical cleanup either wrap with @Reentrant("any") (recommended) or pair the calls themselves.

10.3 Panics across the boundary — @OnPanic

Exported extern functions never unwind through C frames. The decorator picks the policy:

ValueMeaning
@OnPanic("abort") (default)Panic in body → process abort at the FFI boundary. Log message to stderr.
@OnPanic(value)Panic in body → log message; return value (must type-match the declared return type).
 
@OnPanic(-1i32)
extern function process_chunk(buf: *u8, n: usize): i32 {
  if n > MAX { panic("chunk too large") }   // → returns -1
  ...
}

Imports have no in-language panic policy; if the C function aborts or longjmps, the platform's rules apply.

10.4 GC interaction with foreign memory

  • The GC ignores foreign-heap addresses (already in 16-memory.md).
  • Managed pointers inside an extern struct are not traced. The user keeps the target pinned for the struct's lifetime.
  • The cycle collector assumes every mutator thread is at a safe-point or blocked. Threads inside an FFI call (auto-blocked per §10.1) do not stall collection.

10.5 Signal handlers

Running language code from a POSIX signal handler is UB unless the handler is @Reentrant("any") at minimum — and even then, the usual signal-safety rules (no allocation, no locks held by the interrupted thread) apply. Practical advice: don't.

11. Linkage and manifest MANIFEST

[package.links]
zlib    = { lib = "z",      kind = "dynamic", version = ">=1.2" }
mylib   = { lib = "mylib",  kind = "static",  path = "vendor/libmylib.a" }
crypto  = { lib = "crypto", kind = "dynamic" }

[package.ffi]
# Bindings auto-generated from C headers, regenerated when the header changes.
bindings = [
  { header    = "vendor/zlib.h",
    output    = "src/bindings/zlib.lang",
    allowlist = ["inflate*", "deflate*"] },
  { header = "vendor/mylib.h",
    output = "src/bindings/mylib.lang" },
]

# Headers auto-generated from this crate's pub extern functions.
exports = [
  { module = "lib", output = "target/include/mylib.h" },
]

@Link(lib = "name") in source refers to a [package.links] entry. A function with only @Symbol("...") and no @Link resolves from the host process — useful for libc and platform symbols.

lang build runs bindgen automatically for any [package.ffi.bindings] entry whose header is newer than its output, and cbindgen for [package.ffi.exports].

12. Tooling — lang ffi TOOL

lang ffi bindgen <header> [--output <file>] [--allowlist <pat>] [--blocklist <pat>]
                          [--types-only]
        Generate extern struct, extern type, extern function, extern var declarations,
        and pub var constants from a C header. Powered by libclang. Output is
        deterministic — safe to commit.

lang ffi cbindgen [--module <path>] [--output <file>] [--lang <c|c++>]
                  [--header-guard <name>]
        Emit a C header declaring every pub extern function and pub extern struct
        reachable from <module>. Round-trips with bindgen.

lang ffi check [--against <header>] [--strict]
        Verify this crate's extern signatures still match the named C header.
        Reports missing symbols, changed argument types, struct layout diffs.
        Exit 0 if clean, 1 on drift. CI gate.

lang ffi layout [<type>] [--target <triple>] [--format <human|json>]
        Print size, alignment, and field offsets for one or all extern struct types
        in the current crate, for the named target. Debugging ABI mismatches.

Examples:

lang ffi bindgen vendor/zlib.h --output src/bindings/zlib.lang --allowlist "inflate*"
lang ffi cbindgen --module lib --output target/include/mylib.h
lang ffi check --against vendor/zlib.h
lang ffi layout Sockaddr --target aarch64-apple-darwin

Add lang ffi to the subcommand map at 23-cli.md §23.2.

14. Things deliberately not added

Not addedWhy
unsafe { ... } blockThe presence of a *T value in code is already the marker that the language's safety guarantees do not apply. A separate lexical block would be a second marker for the same fact.
defer keywordNot a keyword. Drop covers RAII via PinHandle and CString. Where automatic scope cleanup is genuinely needed (thread attach/detach), use @Reentrant("any") to make the compiler emit it.
union keyword for C unionsDecorator @Union on extern struct does the same job without a new keyword.
const keywordModule-level var initializers are already compile-time constants (17-modules.md §17.6). bindgen emits pub var FOO: T = expr.
static keyword on methodsStatic methods are functions without self (10-interfaces.md §10.1). No prefix needed.
@Repr(C) / @Repr(Lang) on regular structsstruct vs extern struct already conveys this. @Repr would be redundant.
Field-level decorators (@Bitfield, @FlexArray)The macro system permits decorators on items, not fields (22-macros.md §22.2). Bitfields via mask/shift methods; flexible arrays via Foreign.alloc_flex.
Trailing-lambda call syntaxThe language consistently passes closures inside parens (20-concurrency.md, 18-stdlib.md). with_pin(value, |p| { ... }) uses the existing form.
Variadic ... token in signatures@Variadic decorator carries the meaning; no new token. Aligns with 09-functions.md §9.11's "no variadics" general rule.
Const generics for arrays[T; N] exists only inside extern struct fields and extern function signatures. Const generics in the broader language is out of scope.
C++ interopOut of scope. Use extern "C" shims on the C++ side.

Summary

This proposal adds: two operators (&, * prefix), one narrow type form ([T; N] in extern positions), two extern family declarations (extern type, extern var), an as extension for pointer reinterpretation, and a set of decorators on existing item shapes. Everything else — C unions, C enums, opaque types, foreign allocation, pinning lifecycle, threading semantics, panic policy, callbacks, strings — lives in stdlib types and decorators on existing items.

The bigger ABI story (decoupling layout from allocation, threading model, panic policy, tooling) is identical to the previous proposal. The difference is doing it without inventing new keywords, blocks, or syntactic positions where the existing language already has the right pieces.
