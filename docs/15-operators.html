15. Operators & Operator Overloading

Most operators are compiler-lowered syntax over primitive operations or well-known methods on extend blocks. The importable core:prelude contracts cover equality, ordering, hashing, cloning, dropping, iteration, error propagation, stringification, and panic; arithmetic/bitwise operator labels such as Add are protocol names used by the checker today, not exported stdlib interfaces.

1. Arithmetic

// Operator protocol method names recognized by the checker today:
// +  add(self, rhs)
// -  sub(self, rhs)
// *  mul(self, rhs)
// /  div(self, rhs)
// %  mod(self, rhs)
// -x neg(self)

Primitives implement these for matching types. str implements + concatenation for str + str.

extend Vec3 {
  function add(self, k: f64): Vec3 {
    Vec3 { x: self.x + k, y: self.y + k, z: self.z + k }
  }
}

a + b resolves by matching the left operand type and dispatching to its visible add method when one exists; otherwise primitive handling applies.

2. Logical

// !mask on integers means bitwise NOT.
extend i32 {
  function not(self): i32 { ... }
}
Bitwise NOT is !; ~ is an accepted synonym The canonical NOT operator is !. On integers it resolves to the not method (bitwise NOT); on bool it is logical NOT — the compiler picks based on the operand type. The lexer also recognises ~ for users coming from C / Rust; ~x on an integer is desugared to !x in the parser. Prefer ! in new code.

3. Bitwise

// Operator protocol method names recognized by the checker today:
// &   bitand(self, rhs)
// |   bitor(self, rhs)
// ^   bitxor(self, rhs)
// <<  shl(self, rhs)
// >>  shr(self, rhs)
Two key rules
  • Shift right on signed integers is arithmetic (sign-extending).
  • Shifting by >= width(T) panics in both debug and release.
  • | in type position constructs unions; in expression position it uses the bitwise-OR protocol. Context disambiguates.

4. Equality

pub interface Eq {
  function eq(self, other: Self): bool
}

!= is defined by the checker as the negation of eq; there is no separate importable ne method in the current core:prelude.Eq contract.

Primitives have built-in Eq. User types must implement it explicitly — there is no implicit field-by-field equality. Derive with @derive(Eq) (see 22-macros).

5. Ordering comparisons

pub interface Ord {
  function lt(self, other: Self): bool
  function le(self, other: Self): bool
  function gt(self, other: Self): bool
  function ge(self, other: Self): bool
}

Numeric primitives and char implement Ord. str implements Ord (lexicographic by Unicode scalar values). bool and null do not. This comparison contract is separate from the memory-ordering value type in core:sync:atomic.Ordering; comparison operators do not construct or return an Ordering enum.

6. Indexing

Indexing is compiler-recognized syntax for collection-like layouts and future indexable user-type protocols. The stable implemented surface today is the built-in collection behavior for List<T> and Map<K, V>, which panic on [] for missing or out-of-range; use .get(i)/.get(k) for the T | null variant.

Importable Index / IndexMut interfaces are not part of the current stdlib catalog. Adding them as real user-facing interfaces should be a deliberate language-design step, because it changes both the named core:prelude surface and operator dispatch rules.

7. Hashing

pub interface Hash {
  function hash(self): u64
}

Map<K, V> requires K: Eq + Hash. The contract: a.eq(b) implies a.hash() == b.hash().

Primitives implement Hash. str implements Hash. Tuples implement Hash if every component implements Hash.

8. Cloning

pub interface Clone {
  function clone(self): Self
}
Primitives clone trivially. Use @derive(Clone) for field-by-field deep copy.

9. Drop

pub interface Drop {
  function drop(self)
}

Called by the runtime just before reclaiming a managed object. Use to release foreign resources, log, etc.

When drop runs

  • Unreachable object, regular GC — asynchronously, from the finalizer queue, in unspecified order. See 16-memory §8.
  • Program exit — best-effort pass; may skip finalizers entirely.
Drop is asynchronous and not guaranteed drop runs eventually, on a finalizer thread, in unspecified order, only after the collector observes the object as unreachable. It may never run (at program exit, or if the object is leaked). A panicking Drop impl aborts the process. For any resource that needs deterministic release (files, locks, transactions, handles), call the release method explicitly — the language provides no scope-exit hook.
dynamic does not implement Drop The type dynamic itself has no impl. A value stored in a dynamic still runs its underlying Drop when the GC reclaims it — the box's type pointer points at the real type's descriptor. You just can't call .drop() through the dynamic binding without narrowing first. See 12-type-logic §5.

10. Stringification — ToStr

pub interface ToStr {
  function to_str(self): str
}
String interpolation desugars to ToStr-based concatenation.

Built-in implementations

  • Numeric primitives — decimal representation.
  • bool — "true"/"false".
  • char — single-character str.
  • str — identity.
  • null — "null".
  • List<T> — "[a, b, c]" (requires T: ToStr).
  • Map<K, V> — "{k1: v1, k2: v2}" (requires both implement ToStr).
  • Tuples — "(a, b, c)" (every component must implement ToStr).

Auto-derive

@Derive(ToStr)
pub struct Person { pub name: str, pub age: i32 }

// Person { name: "Alice", age: 30 } produces:
// "Person { name: Alice, age: 30 }"
Language-level stringification uses ToStr Interpolation and value as str both lower through ToStr. The library-level std:fmt module adds ordinary Display and Debug contracts for APIs that need to distinguish user-facing and developer-facing rendering, but those contracts do not change interpolation semantics.

For numeric primitives, value as str is sugar for value.to_str() — keeping one stringification path through the type system.

dynamic does not implement ToStr Interpolating a dynamic binding ("$d") is a compile error. Narrow first — usually if d is ToStr { … } — and call to_str() in the branch. The same applies to Clone, Eq, Hash, and Ord: none of them dispatch through dynamic. See 12-type-logic §5.

11. ReprC — disabling object header for FFI

pub interface ReprC { }

Marker interface (no methods). Implementing ReprC asks the compiler to lay out the struct without the two-word object header — standard C struct layout, suitable for FFI.

Prefer extern struct A ReprC struct loses the ability to be referenced from managed code as a normal heap object — the GC cannot trace it. In practice, prefer extern struct (see 19-ffi). ReprC is for the rare case where a struct must be both managed-accessible and C-layout. Cross-tracing rules are unspecified; mark them only if you understand the implications.

12. Precedence summary

The canonical precedence table is in 07-expressions §5. Overload method calls do not see their own precedence — precedence is fixed at the operator level.

Non-associative comparisons == and != are non-associative. <, <=, >, >= are also non-associative. a < b < c is a parse error.

13. Operator overloading and dispatch

Resolved operator method calls follow the same monomorphization rules as any other method call (see 11-generics). Interface-backed operators such as Eq.eq and Ord.lt use the normal interface dispatch path when the operand is interface-typed.

14. No bespoke operator definitions

No new operators You can only overload the operators in §Map by implementing the corresponding protocol method. There is no way to define new operator symbols or override operator precedence per-type.
