3. Discriminated Unions

A union is a type whose value is exactly one of a fixed set of variants. Set-like semantics — order doesn't matter, duplicates collapse, nested unions flatten.

1. Anonymous & named unions

The alias is structural sugar — any two unions with the same variant set are the same type.
type Result = i64 | str | null

function find(id: i64): Person | null { ... }      // inline
type Maybe<T> = T | null                            // alias
function find(id: i64): Maybe<Person> { ... }
The universal union — dynamic There is also a built-in type dynamic, conceptually the union of every type in the program — but written as a single name, not a pipe enumeration. It exists for boundary code (decoded JSON, plugin APIs, heterogeneous collections) and uses the same is/as narrowing as ordinary unions. Full rules in 12-type-logic §5.

2. Normalization — order, duplicates, flattening

The compiler treats unions as sets of variants. Three rules run during type checking:

one tag identifying which of i64, str, bool is inhabited. There is no two-level tag — flattening applies through aliases as well. 1 tag byte (plus payload) never 2 no nested tags
After normalization, every union has a canonical, finite set of non-union variants.

3. Recursive unions

A type alias may reference itself, but only through a non-union variant — typically a struct field. A recursive union built only from unions and the alias name itself reduces to a non-recursive one.

✓ Through a struct field

struct Cons {
  head: i64,
  tail: List
}
type List = null | Cons

// List recurses through Cons.tail
// Flattening does NOT cross struct
// field boundaries.

✗ Direct self-reference

type X = i64 | X

// Normalizes to:
// X = i64 | X = i64 | i64 = i64

Mutual recursion through unions normalizes the same way: X = i64 | Y, Y = str | X both reduce to i64 | str.

A struct field is one variant, not a union — recursion through it stays cleanly typed.

Normalization algorithm — informal

  1. Substitute alias references that resolve to unions.
  2. Flatten nested union expressions.
  3. Remove occurrences of the alias being defined from its own RHS (X | X ≡ X).
  4. Remove duplicate variants.
  5. Check that the resulting variant set is finite and non-empty.

4. Subtyping by union extension

A union A | B is implicitly a subtype of A | B | C.
var x: i64 = 5
var y: i64 | str       = x   // OK: widening
var z: i64 | str | bool = y  // OK: widening further

5. Generic unions

Type parameters are substituted before normalization. This composes elegantly:

type Result<T, E> = T | E

// Result<i64, str>        = i64 | str
// Result<i64, i64>        = i64                     (deduplicated)
// Result<i64 | str, bool> = i64 | str | bool       (flattened)

type Maybe<T> = T | null
// Maybe<i64>        = i64 | null
// Maybe<i64 | null> = i64 | null                   (deduplicated)
// Maybe<Maybe<T>>   = Maybe<T>                      (collapses)
No "double-nullable" Maybe<Maybe<T>> is the same as Maybe<T> — there is no Some<None> ambiguity. Where the ambiguity actually matters (iterator end signalling, future readiness), use a dedicated wrapper struct — see Item<T> in 18-stdlib and Ready<T> in 21-async.

6. Pattern matching

See 07-expressions for match syntax and 12-type-logic for is/as and flow narrowing.

Exhaustiveness match over a union must be exhaustive. Every variant must be covered, either explicitly or via _. Missing variants are a compile error with the full list of misses.

Variant identity

Two variants are the same if they refer to the same nominal type. Structural types (tuples) compare by shape — so (i64, i64) | (i64, i64) collapses to (i64, i64).

Empty unions are not allowed There is no type X = (zero variants). Every union must have at least one variant. One-variant "unions" are equivalent to the underlying type.
