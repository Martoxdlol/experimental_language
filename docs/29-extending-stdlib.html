29. Extending the Standard Library

This chapter is the contributor guide for adding, organizing, or replacing core:* and std:* modules. It complements the public stdlib surface in chapter 18, the extended module roadmap in chapter 24, and the sysroot/toolchain model in chapter 23.

The standard library is infrastructure, not compiler folklore. Every importable toolchain module must have an explicit catalog entry, a documented public surface, tests for success and failure paths, and a clear implementation kind. If a behavior is Rust-backed, the Otter-facing contract must still be visible as ordinary core:* or std:* API.

1. Principles

  • core:* is language substrate. It is for things the compiler/runtime treats specially: desugar targets, runtime-recognized layouts, privileged handles, syntax protocols, and macro/compiler APIs.
  • std:* is the official library. It contains ordinary toolchain-shipped APIs whether they are fully portable or target-backed: filesystem, networking, clocks, process state, randomness, terminal I/O, but also shared value types such as errors, JSON, HTTP, formatting, and portable I/O interfaces.
  • Authority beats portability. An API does not belong in core: merely because it can run without an OS. If users could implement the same semantics in a normal package, it belongs in std: or pkg:.
  • The prelude stays near-empty. Syntax may desugar through hidden compiler knowledge, but every name that a user spells must be imported from a documented module.
  • No accidental globals. Adding a definition to the hidden toolchain module does not make it public. Public availability comes from a catalog export.
  • No target policy in random compiler code. Target differences flow through stdlib providers/sysroots, not through scattered special cases in name resolution.

2. Module kinds

KindUse whenExamples
Otter The surface and behavior can be authored in Otter Fusion source: interfaces, value wrappers, adapters, pure helpers, and portable library logic. std:error, std:bytes, std:fmt, std:time.Duration, std:fs.Path, std:fs.DirEntry, core:sync:atomic.Ordering, std:hash, std:http, std:net:types
RustBacked The behavior is a compiler/runtime intrinsic, and the Otter surface is a small importable marker or function set. std:io.print, std:io.eprintln, core:prelude.panic, std:process.exit/abort, future target-only hooks and provider shims
Mixed The public API is ordinary Otter Fusion, but some operations call Rust runtime hooks or compiler intrinsics. std:io, core:ffi, std:sync, std:fs.File handles and file helpers, std:time.Instant/SystemTime, std:process host environment/execution helpers, std:rand.OsRng/ThreadRng

The implementation kind is descriptive and architectural. It does not create a separate import syntax. Users still write normal imports such as import { Error } from "std:error" or import { println } from "std:io".

3. The stdlib catalog

The compiler-side catalog currently lives in crates/compiler/src/sema/stdlib.rs. It records the importable module path, tier, implementation kind, and exported names for every built-in core:*/std:* view.

Otter-authored toolchain definitions live beside the catalog under crates/compiler/src/sema/stdlib_src/, split by public tier: stdlib_src/core/*.otter for compiler/runtime substrate and stdlib_src/std/*.otter for ordinary standard-library modules. The compiler collects the bundled source files through the explicit TOOLCHAIN_SOURCES manifest into hidden module-local owners under the private __builtins__ root, then builds curated import views from the catalog. This preserves the near-empty prelude rule while giving stdlib code a real module-shaped home and allowing duplicate local names in different std:*/core:* modules.

StdModuleSpec {
  path: &["std", "error"],
  tier: StdTier::Std,
  implementation: StdImplementation::Otter,
  exports: &["Error", "Annotated", "with_context"],
}

Name resolution builds curated views from the active StdProvider. The built-in provider is the only provider today, but the trait boundary is deliberate: future target sysroots can expose a different catalog without changing source-level import semantics.

Catalog exports are an API boundary. Do not export helper structs, iterator adapters, runtime marker internals, or compiler-only glue just because they exist in hidden toolchain source owners.

Malformed provider entries are rejected before they become importable views. Duplicate module paths, root-only paths, unaddressable path segments, tier/root mismatches, duplicate exports, and missing exported symbols all produce provider diagnostics instead of silently exposing a partial or wrongly-tiered core:*/std:* module.

4. Adding a core:* module

Add a core:* module only when the compiler/runtime needs privileged knowledge of the API. Good candidates are syntax protocols, compiler desugar targets, runtime-recognized layouts, FFI substrate, macro/compiler APIs, and collection types whose literals/indexing are compiler-lowered.

  1. Specify the public surface in chapter 18 or chapter 24.
  2. Author the Otter Fusion definitions in crates/compiler/src/sema/stdlib_src/core/<module>.otter, or split a larger substrate module into a clearly named file under that directory.
  3. Add a StdModuleSpec entry with StdTier::Core and the correct StdImplementation.
  4. Export only the names that the module publicly promises.
  5. Add import-resolution tests proving the names are available only through the documented explicit import path.
  6. Add typechecker/codegen/e2e tests for the behavior, including compile-error tests for missing imports and wrong use.
  7. Update examples, docs, LSP expectations, and ROADMAP.

A core:* module must not be added merely for convenience or portability. If the API is ordinary library surface, put it in std:*. If it later needs host services, the provider can supply a target-backed std:* implementation without changing source imports.

5. Adding a std:* module

Add a std:* module when the API is official toolchain library surface but not language substrate. This includes both portable contracts and host-backed capabilities: errors, formatting, JSON, HTTP value types, files, networking, clocks, process state, randomness, terminal streams, native threads, and target-managed resources.

  1. Identify the corresponding portable std:* contract, or add one first if the shape is universal. For example, std:fs.File should implement std:io.Reader/Writer/Seeker rather than inventing file-only read/write protocols.
  2. Author Otter Fusion surface definitions in crates/compiler/src/sema/stdlib_src/std/<module>.otter. Keep pure interface/value-shape code there even when behavior is Rust-backed.
  3. Decide whether the module is RustBacked or Mixed. Most real std:* modules will be Mixed: Otter API types over Rust runtime hooks.
  4. Add the runtime hooks and backend calls needed by the implementation. JIT and native builds must link and behave the same way.
  5. Add the StdModuleSpec entry with StdTier::Std.
  6. Add tests for ordinary imports and for no-std rejection. A package marked no-std must get a hard error on std:* imports.
  7. Document target assumptions and future provider behavior. If the module cannot exist on some targets, specify the absence as provider behavior rather than a silent partial implementation.
Prefer portable contracts. The source path std:fs should mean "the filesystem package for this target", not "POSIX filesystem forever". POSIX, WASI, embedded, and sandboxed providers can supply different implementations while preserving the same documented surface.

6. Adding Rust-backed behavior

Rust-backed behavior is allowed, but it must remain visible as a language-level contract. Do not make a new builtin by only special-casing the checker or backend.

Runtime hooks

  • Runtime functions live in the appropriate crates/runtime/src/*.rs module.
  • Externally-called runtime hooks use the existing lang_* ABI naming pattern until that runtime ABI is renamed project-wide.
  • Hooks must define ownership, pinning, allocation, panic, and GC-root behavior explicitly.
  • Anything that can allocate, block, suspend, panic, or hold a resource needs tests for that behavior.

Backend calls

  • Backend lowering belongs near the feature using it, not in a catch-all path.
  • Generated calls must be shared by JIT and native builds.
  • Native builds must link required support libraries deterministically.
  • GC and reference-counted resources must be rooted/released across all exit paths, including panic and cancellation when applicable.

Otter surface

Even for RustBacked modules, users import names from a normal module. The compiler may recognize those names internally, but the documented API remains the source contract.

7. Custom providers and sysroots

A provider is a catalog of toolchain modules for a target. Today the CLI still selects the built-in provider, but semantic collection already accepts an explicit StdProvider; tests use that hook to prove a target catalog can add custom std:* views over collected toolchain source, omit unsupported std:* modules, and leave listed core:* substrate available. Future compiler configuration will select a provider and its external source/sysroot layer from the active target/sysroot:

~/.otter_fusion/toolchains/<channel>/lib/sysroot/<triple>/ core/ std/ manifest.toml abi.json

Provider behavior:

  • A provider may replace a std:* module implementation for a target.
  • A provider may omit a std:* module when the target cannot support it.
  • If a known toolchain module is omitted by the selected provider, import resolution reports that provider's name rather than treating the path as an unknown module.
  • A provider may add target-specific std:* modules gated by manifest/sysroot configuration. Today tests exercise this with a provider-added view over bundled source; external sysroot source loading is future work.
  • A provider should keep core:* stable. Replacing core:* is an advanced sysroot operation and must preserve language ABI, compiler expectations, and semantic contracts.
  • Provider identity, ABI version, and exported module set must be lockfile- and diagnostic-visible once external sysroots are implemented.

Ordinary packages must not shadow std:* through pkg:. A custom standard library is a toolchain/sysroot choice, not a dependency-resolution trick.

8. Imports, prelude, and exports

  • core: and std: paths are absolute. They do not depend on the importing package's module tree.
  • Every spelled name requires an import, including standard library names such as List, Map, Error, println, and Thread.
  • Adding a name to the hidden toolchain module is insufficient. It must be listed in the corresponding catalog entry's exports.
  • Ambient imports activate extension methods, following the normal module rules in chapter 17.
  • Re-exports from stdlib modules must be explicit and documented. Avoid accidental umbrella modules until the public surface has settled.
  • Provider catalog exports are validated against the collected toolchain source; a provider must not advertise a symbol that its source/sysroot layer does not define, and each module's export list must not contain duplicates.
  • Provider module paths must include both a scheme and module path, must use addressable import-path segments (no empty, ., .., or embedded / segments), must be unique, and their tier must match the path root: StdTier::Core for core:*, StdTier::Std for std:*.

9. Required tests

Every stdlib addition needs tests at the level of risk it introduces. For new modules, the default expectation is broad coverage, not a single happy-path case.

AreaRequired coverage
Catalog Unique paths, tier/path agreement, unique exports, provider lookup, provider-added modules, and implementation kind coverage, including provider-export materialization. Every catalog export must also appear in a focused require-import negative e2e case; the stdlib catalog tests scan those diagnostics and fail if a newly exported name lacks import-gating coverage.
Imports Explicit import success, missing import failure, unavailable module failure, namespace imports, named imports, and ambient extension activation when relevant.
Type checking Correct signatures, generic inference, interface bounds, dynamic dispatch, coercions, and negative cases.
Runtime/codegen JIT/native parity, panic behavior, allocation behavior, resource release, concurrency/async behavior, and GC-stress where relevant.
Tooling LSP hover/goto/completion expectations when new public names appear, plus docs and examples that compile.

For compile-error cases, prefer dedicated files under tests/cases/errors or a focused stdlib error directory once that layout exists. For runtime behavior, add e2e cases under the closest feature directory and keep examples updated.

10. Review checklist

  • required The module belongs in the chosen tier: core:* for compiler/runtime substrate, std:* for official library APIs and target-backed implementations.
  • required The public surface is documented in chapter 18 or chapter 24 before implementation details are treated as stable.
  • required The catalog entry lists the correct StdTier, StdImplementation, path, and exports.
  • required All public names require explicit imports unless they are syntax-only compiler desugar targets.
  • required Rust-backed hooks have clear ownership, GC, panic, blocking, and native-linking behavior.
  • required Tests include success, failure, import, and runtime/codegen cases appropriate to the module.
  • required ROADMAP, goals, docs index, examples, and LSP expectations are updated when the public surface changes.
Ask before changing language design. Adding a module is normal stdlib work. Changing import semantics, prelude rules, orphan rules, ownership semantics, async behavior, ABI, or the meaning of core:/std: is language design work and needs an explicit decision.
