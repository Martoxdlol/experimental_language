Build profiles and backend optimization. The current run --release, exec --release, and build --release flag selects release arithmetic semantics and asks the Cranelift backend for speed-oriented machine-code optimization. Debug remains the default because its generated IR is easier to inspect with otter_fusion emit clif. Normal executable codegen is root-seeded: run/build start from main, and isolated test/bench children start from the exact requested body. Calls, closures, async jobs, vtables, generic instances, and Drop finalizers are still discovered lazily as reachable code demands them, so unused helpers and untouched stdlib functions are not emitted into the final JIT/object artifact.

4. otter_fusion build — the main path

Output layout under target/:

target/ ├── <profile>/ # debug/, release/, custom-foo/ │ └── <triple>/ # x86_64-darwin/ │ ├── bin/<name> # executables │ ├── lib<name>.{a,dylib} # libraries │ ├── deps/ # per-crate objects & metadata │ ├── build/ # build-script outputs │ ├── incremental/ # incremental cache │ └── examples/, tests/, benches/ ├── cache/ # content-addressed: ASTs, type tables, IR ├── doc/ # output of `otter_fusion doc` └── tmp/ # transient files when --keep-temps
Incremental & idempotent Hashes of (source bytes + manifest + toolchain version + cfg set + dep fingerprints) key into target/cache. Switching profiles never invalidates the other profile's cache.

6. Sysroot & --sysroot

~/.otter_fusion/toolchains/<channel>/lib/sysroot/<triple>/ ├── core/ # source + prebuilt .ottermeta + .a ├── std/ # source + prebuilt .ottermeta + .a └── manifest.toml # versions, supported targets, ABI hash

Resolution order: --sysroot CLI override → [build] sysroot in manifest → OTTER_FUSION_SYSROOT env var → active toolchain's default.

You want…Mechanism
Different core: substrate (advanced compiler/runtime contract)[build] sysroot = "<path>" where path/core/manifest.toml declares it provides core.
Different std: provider (portable APIs and target shims)Same, providing std.
Build the sysroot from sourceotter_fusion sysroot build --features … --target <triple>
Drop std: entirelyManifest [package] no-std = true. std:* import → hard error.
Sysroot ABI mismatch A sysroot is a versioned, ABI-tagged artifact. The driver refuses to link an object compiled against sysroot ABI X into a binary linking sysroot ABI Y, with a diagnostic showing the two hashes.

7. Dependency model

Rust model + sparse-index by default + content-addressed cache with hardlinks (pnpm's good idea).
Key properties
  • No nested copies. Each version of each package is downloaded once, compiled once per (profile, features, target).
  • One version per (name, semver-compatible range). Resolver unifies ^1.2 + ^1.4 → 1.4. Different majors can coexist.
  • Lockfile is truth, manifest is constraint.
  • No runtime path resolution. The compiler never walks the filesystem for packages — only --extern flags + sysroot.

When different semver-compatible ranges of the same package name appear in the graph, the resolver keeps them as distinct package instances. Source still uses the ordinary location-free form (pkg:shared), but that name is resolved in the importing package's dependency context: a root module sees the version declared by the root manifest, while an external package sees the shared instance selected by its own manifest/lockfile edge. Commands that display or copy dependencies keep this unambiguous: tree and why include versions when a name appears more than once, and vendor uses name-version directories only for duplicate names.

Lockfile rules

  • Binary packages: project.lock must be committed.
  • Library packages: project.lock is generated for the lib's own dev/test builds but is ignored by consumers.
  • --locked / --frozen / --offline are the CI / reproducibility levers.
  • otter_fusion lock --check is the CI gate: fails if a build would mutate the lockfile.

Lockfile contents

Each resolved package pins an exact version, its source, and a content hash. The sha256 is verified on every fetch and extraction — a mismatch is a hard error, never a silent re-download. The lockfile is generated; do not hand-edit it.

# project.lock  (excerpt)
version = 4

[[package]]
name     = "serde"
version  = "1.2.7"
source   = "registry+https://pkgs.example.dev/index"
checksum = "sha256:9f8b…c41a"

[[package]]
name     = "foo-local"
version  = "0.1.0"
source   = "path+../foo"            # path deps carry no checksum

[[package]]
name     = "bar-git"
version  = "0.4.0"
source   = "git+https://…#abc123"   # pinned to the resolved commit

Git dependencies are fetched at resolution time through a bare mirror cache under ~/.otter_fusion/git/cache/. rev, branch, tag, and unpinned default-branch dependencies all resolve to an exact commit; the immutable checkout is materialized at ~/.otter_fusion/git/<url-hash>/<rev>/. The lockfile records git+<url>#<rev> plus a deterministic source-tree checksum. Existing locks keep branch/tag/default dependencies pinned until an update-style resolve ignores the old lockfile and refreshes the moving reference.

Registries & the registry protocol

A registry is a named index the resolver maps pkg: dependencies to. The default registry and any extras are declared in the manifest / ~/.otter_fusion/config.toml (see §8). The location of a package never appears in source — import paths stay location-free (import … from "pkg:foo/bar"); where a package comes from lives entirely in the manifest and lockfile. Fetching a raw remote file is a different operation behind its own reserved scheme family (17 §17.14) — there is no pkg+https://… import form.

The wire protocol is the sparse HTTP index: the client fetches only the per-package metadata files it needs over https, never a full clone. The index root serves a config.json:

{
  "dl":  "https://pkgs.example.dev/api/v1/{crate}/{version}/{sha256-checksum}.tar.gz",
  "api": "https://pkgs.example.dev",
  "auth-required": false
}
KeyMeaning
dlTarball download URL template. Markers {crate}, {version}, {prefix}, {sha256-checksum} are substituted; if none are present, /{crate}/{version}/download is appended.
apiBase URL for write/query operations (publish, yank, search, login). Optional; without it those commands are unavailable.
auth-requiredPrivate registry — every request (index, download, API) carries credentials from ~/.otter_fusion/credentials.toml.
Artifacts are tarballs, verified by hash A package is a .tar.gz resolved through dl, extracted into the content-addressed store at ~/.otter_fusion/registry/src/ and keyed by its sha256. The same checksum is recorded in the lockfile, so a registry cannot serve different bytes for an already-locked version without the build failing.

otter_fusion publish uploads the tarball with a metadata sidecar carrying the package name/version and sparse-index dependency edges: dependency name, version requirement, optional flag, default-feature flag, enabled feature list, non-default registry name, plus the package's [features] map. The built-in registry persists that metadata into the JSON-lines index so later resolver runs can pull transitive dependencies and honor feature-gated optional dependencies from published packages. Registry-published packages must use registry dependencies; publishing a manifest with path or git dependencies is rejected because downstream sparse-index consumers cannot resolve those local or repository-specific sources from the registry.

Path-form mapping

Every import path carries an explicit scheme (see 17 §17.4); the column below shows the path written as import { … } from "<path>" and what the driver hands the compiler.

Path in sourceCompiler input
"self:util/log"module-tree root form → known file in this package
"self:./sib", "self:../up"relative module-tree lookup → known file
"file:../shared/x"literal filesystem path (allowlisted in project mode; unrestricted in direct mode)
"pkg:foo/bar"resolved via lockfile + registry → --extern foo=<meta>, then look up bar in foo's pub tree
"core:prelude", "std:io"sysroot

8. Manifest — project.toml

[package]
name = "myapp"
version = "0.3.1"
kind = "binary"                # or "library", "library+bins"
entry = "src/main.otter"
edition = "2026"
no-std = false
default-features = ["json"]

[dependencies]
serde     = "1.2"                                   # default registry
http      = { version = "0.4", features = ["tls"] }
internal  = { version = "2.0", registry = "myco" }  # from a named registry
foo-local = { path = "../foo" }                     # local path
bar-git   = { git = "https://...", rev = "abc123" } # git, pinned to a rev

[registry]
default = "public"             # which registry bare `pkg:` deps resolve against

[registries]
public = { index = "sparse+https://pkgs.example.dev/index" }
myco   = { index = "sparse+https://pkgs.internal/index", auth = true }

[features]
json = ["dep:serde"]
default = ["json"]

[profile.release]
opt-level = 3
lto = "thin"
debug-info = "line"
strip = "debug"
panic = "abort"
codegen-units = 1

[target.x86_64-linux-gnu]
linker = "lld"
otterflags = []

[scripts]                      # `otter_fusion run-script `
ci = "otter_fusion fmt --check && otter_fusion lint && otter_fusion test"

Feature resolution is part of dependency resolution. The resolver starts from the package's default feature set ([features] default, plus any [package] default-features aliases), expands feature entries transitively, and includes optional = true dependencies only when an active feature names them with dep:name (or requests one of their dependency features with name/feature). Enabled dependency features are carried into registry resolution, and the sparse-index metadata sidecar published by otter_fusion publish stores the package feature map so downstream consumers can resolve feature-gated optional transitive dependencies.

9. FFI & linking

The source-level FFI surface is in 19-ffi. The CLI layer covers three concerns: declaring native libraries to link, generating bindings from C headers, and emitting C headers for exported functions.

[package.links]
zlib    = { lib = "z",      kind = "dynamic", version = ">=1.2" }
mylib   = { lib = "mylib",  kind = "static",  path = "vendor/libmylib.a" }

[package.ffi]
bindings = [
  { header    = "vendor/zlib.h",
    output    = "src/bindings/zlib.otter",
    allowlist = ["inflate*", "deflate*"] },
]

exports = [
  { module = "lib", output = "target/include/mylib.h" },
]

otter_fusion ffi subcommands

CommandPurpose
otter_fusion ffi bindgen <header>Generate extern declarations from a C header (libclang). Deterministic output — safe to commit.
otter_fusion ffi cbindgenEmit a C header for pub extern items in a module. Round-trips with bindgen.
otter_fusion ffi check --againstVerify extern signatures match a named C header. CI gate.
otter_fusion ffi layoutPrint size / alignment / field offsets for extern structs, target-aware.

Build scripts

[build-script]
file = "build.otter"           # compiled and run before the main build

Writes link directives on stdout:

otter_fusion:link-lib=dylib=z
otter_fusion:link-search=native=/opt/lib
otter_fusion:rerun-if-changed=vendor/libmylib.a
otter_fusion:emit-cfg=has_openssl
otter_fusion:ffi-bindgen=vendor/generated.h:src/bindings/generated.otter
Build scripts are arbitrary code Not run under otter_fusion check. Sandboxed when possible (filesystem read-only outside OUT_DIR). The driver prints a clear "running build script for <pkg>" line so they are never silent.

13. Things easy to miss

Checklist of small things that bite later
  • Stable diagnostic codes (E0123) — wire otter_fusion explain from day one.
  • --deterministic flag — forbids timestamps, ASLR'd hashes, parallel-codegen reordering.
  • --print introspection: otter_fusion --print sysroot|target-list|cfg|target-features|file-names.
  • Color env vars: respect NO_COLOR, CLICOLOR, CLICOLOR_FORCE.
  • CI-friendly output: --message-format short|json|human; no ANSI in non-TTY unless --color always.
  • Editor format-on-save: otter_fusion fmt --check for CI, otter_fusion fmt --emit stdout for editors.
  • --dry-run on every destructive command (publish, update, clean, vendor, remove).
  • otter_fusion clean granularity: --profile, --target, --package, --doc.
  • External subcommands: otter_fusion foo → otter_fusion-foo on PATH. Community tools without core changes.
  • Hook points: build scripts vs proc macros vs plugins — three distinct, documented mechanisms.
  • otter_fusion audit — vulnerability DB endpoint from day one.
  • otter_fusion self update — toolchain manages itself.
  • Standard OUT_DIR and OTTER_FUSION_* envs — document them as stable contract.
  • "What would change" resolver mode: otter_fusion update --dry-run --verbose printing the lock diff.
  • Single-file ABI for shipping libraries: .ottermeta with explicit compatibility policy.
  • Shell completions: bash|zsh|fish|powershell|nushell.
