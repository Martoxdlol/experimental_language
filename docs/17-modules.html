17. Modules and Imports

A module is the unit of source organization and visibility. One source file is exactly one module (with the exception of inline mod blocks; see 17.2). The module tree is built from explicit mod declarations and mirrors the filesystem.

17.1 Project layout

A project has:

  • A manifest file at the project root (toolchain-defined name; treat project.toml as the placeholder).
  • A source root, conventionally src/, declared in the manifest.
  • An entry file declared in the manifest:
    • Binary: kind = "binary", entry = "src/main.otter". main.otter must export function main(). The package produces an executable; it is not consumable via pkg:.
    • Library: kind = "library", entry = "src/lib.otter". The package's public API is everything pub in lib.otter. Consumers import { ... } from "pkg:<name>" resolve against lib.otter.
    • Library + binaries: kind = "library+bins", plus bins = ["src/bin/<name>.otter", ...]. The library entry is lib.otter; each bin is an additional entry the compiler walks.
  • Dependencies declared in the manifest, available under the pkg: prefix.
Three project kinds. The compiler walks the mod tree starting at each entry.

The compiler starts at each declared entry and walks the mod tree (see 17.2). Every .otter file under src/ must be reachable from some entry through a chain of mod declarations. A source file that no mod declaration mentions is a hard error:

unreferenced source file: src/util/dead.otter
  expected `mod dead` in src/util.otter (or an ancestor)

This is the same strictness as Rust: if it's not in the mod tree, the compiler doesn't see it.

17.2 Module declarations

A file declares its submodules with mod or pub mod:

// src/lib.otter
mod internals          // private — usable from this file, not visible to pkg consumers
pub mod util           // public — pkg:cool-lib/util is a valid import path for consumers
pub mod db

Two forms, exactly:

  • mod <name> — submodule exists; addressable from this file (and its other submodules) but not from importers of this module.
  • pub mod <name> — submodule exists; addressable both internally and from importers of this module.

Resolution to files

A mod foo in file path/to/parent.otter resolves to path/to/parent/foo.otter. The submodule directory shares its parent file's basename.

Top-level entries are the one exception: mod foo in src/lib.otter (or src/main.otter, or any file directly named in bins) resolves to src/foo.otter — siblings of the entry, not src/lib/foo.otter. This matches Rust's crate-root convention and keeps the source root flat.

src/
  lib.otter                 // entry: mod util, pub mod db, mod internals
  util.otter                // mod helpers, mod parser
  util/
    helpers.otter           // mod text
    helpers/
      text.otter
    parser.otter
  db.otter                  // pub mod query
  db/
    query.otter
  internals.otter

There are no mod.otter index files. Every module's source file is named after itself.

pub mod external, mod private. The compiler errors on any .otter file not reachable from an entry's mod chain.

Inline modules

A mod declaration may carry a body, defining the module inline:

mod conversions {
  pub function as_celsius(f: f64): f64 { (f - 32.0) * 5.0 / 9.0 }
  pub function as_fahrenheit(c: f64): f64 { c * 9.0 / 5.0 + 32.0 }
}

Inline modules cannot have external children: declaring mod foo (no body) inside an inline mod parent { ... } is a compile error. (To split out children, make parent an external module first.) Inline mod inside inline mod is fine.

What mod does not do

  • It does not import names. Use import (17.3) to bring names into scope.
  • It does not auto-execute the submodule's code (there is no module-load code; see 17.6).
  • It does not change a file's contents in any way — it just registers the file's existence in the module tree.

17.3 Import forms

Three forms, distinguished by what they contribute to the current module: just extensions, a namespace, or specific names.

import "pkg:my_module"                                   // ambient — extensions only, no names bound
import "pkg:my_module" as M                              // namespace bind to M
import { Foo, bar }      from "self:util/helpers"        // named
import { Foo as Bar }    from "self:util/helpers"        // named with alias
import { Foo, bar as baz, Qux } from "self:util/helpers" // mixed
Three forms, three jobs. Forms compose — you can use all three against the same path.

Ambient form — import "<path>"

The bare form binds no names. Its only effect is to activate the target module's extensions (extend blocks). Use it when you want a module's extension methods available on existing values without bringing any other names into scope:

import "pkg:iter_ext"                  // activates extension methods on Iterator<T>
                                       // no other names from iter_ext are bound

var doubled = numbers.my_map { it * 2 }

Namespace form — import "<path>" as <Name>

Binds the module to <Name>; access members via .:

import "pkg:json" as Json

var v = Json.parse(text)
var s = Json.stringify(v)

The namespace name is required — there is no auto-derivation from the path. Pick a name that's meaningful at the call site.

Named form — import { ... } from "<path>"

Brings exactly the listed names into the current scope. Each name may be aliased with as:

import { Logger }                from "self:util/log"
import { open, close as shut }   from "self:io/file"
import { Foo, Bar, baz }         from "pkg:lib"

Extensions always activate

Every form activates the target module's extensions. There is no way to import names without also activating extensions — extend blocks are anonymous (see 10-interfaces.html) and hitch a ride on the module itself.

The orphan rule (10.9) constrains extensions to live in either the type's or the interface's defining module — so the set of "which extensions could come from this import?" is small and statically determinable.

Combining forms

A file may use multiple forms against the same path; their effects compose:

import "pkg:lib" as Lib
import { Foo }   from "pkg:lib"        // both Lib.Foo and bare Foo work

import "pkg:iter_ext"                  // ambient only
import { my_helper } from "pkg:iter_ext"   // also bring a name

Importing the same local name twice (or aliasing into a colliding name) is an error — see 17.9.

17.4 Path forms

Every import path carries an explicit scheme prefix. There is no prefix-less form — the scheme makes the path's origin unambiguous from a glance, and keeps every path greppable. Whether a given scheme is available depends on the run mode (see 17.13): pkg: and the self: root form need project context.

Five scheme prefixes. The scheme tells you where the path resolves — and whether it can leave the package.

Path examples (with source root src/):

import { Logger } from "self:util/log"         // src/util/log.otter (from package root)
import { open }   from "self:io/file"          // src/io/file.otter
import { Helper } from "self:./helper"         // module in the same directory
import { Util }   from "self:../shared/util"   // module in a sibling directory
import { parse }  from "pkg:json/parse"        // external package, subpath
import { rows }   from "file:./fixtures/data"  // raw file path, outside the mod tree

self: vs file:

Both can carry ./ and ../, but they resolve differently:

  • self: walks the explicit module tree. The target must be a declared module, it obeys pub/pub mod visibility, and it cannot escape the package boundary (the source root). This is the everyday way to reach code in your own package.
  • file: takes the relative path literally against the filesystem. It is not a module-tree lookup and is the looser escape hatch — it may point outside the package. Because that breaks the package's hermeticity, an escaping file: path must be explicitly authorized in the manifest (project mode); in direct mode with no project, file: is unrestricted (17.13).

Authorize escaping file: paths with an allowlist of roots/globs:

# project.toml
[file-imports]
allow = ["../shared", "assets/**"]   # a file: path that resolves outside these is a compile error

self: escape rule

The self: relative forms (self:./ / self:../) are convenient for "next to me" and "directly above me" references, but they cannot escape the package boundary. The package boundary is the source root.

src/
  app/
    main.otter                  // can import "self:../util/log" (resolves to src/util/log.otter)
    db/
      query.otter               // can import "self:../../util/log" (resolves to src/util/log.otter)
                               // CANNOT import "self:../../../something"  ERROR: escapes package
  util/
    log.otter

Any self:../ chain that resolves above the source root is rejected by the compiler:

self import "self:../../../outside" escapes package "myapp"

The same rule applies inside external packages: a file in pkg:cool-lib/... cannot self:-import out of cool-lib. Each package is its own escape boundary. The only way to reach another package's contents is its pkg: prefix (and only the names that package marks pub in its entry/library file). When you genuinely need a file outside the package — a shared asset, a generated fixture — that is precisely what file: (with a manifest allowlist) is for.

Each package is its own escape boundary. The only way to reach another package is its pkg: prefix.

Style guidance (lint, not error)

  • Prefer the self: root form (self:util/log) for cross-cutting modules (logging, types, constants) — the path stays meaningful in error messages and grep results.
  • Prefer the self: relative form (self:./, self:../) for tightly-coupled siblings or children — the path stays valid if the subtree moves to a different location.
  • Reach for file: only for genuine non-module data (assets, fixtures, generated blobs) — never to pull in code that could be a declared module. Code belongs in the mod tree, reached via self:.

17.5 Visibility

There are two visibility knobs, no others:

  • pub on an item — the item is visible to importers of this module.
  • pub mod — the submodule is visible to importers of its parent module.

Together they form a chain. For a name to be reachable from outside the package, every mod along the path from the entry must be pub mod, and the leaf item must be pub.

// src/lib.otter
pub mod util       // util is part of the public surface

// src/util.otter
pub mod log        // util/log is part of the public surface

// src/util/log.otter
pub struct Logger { ... }    // Logger is visible to outside callers
struct Internal { ... }       // Internal is NOT visible to outside callers

If lib.otter had written mod util (no pub), the entire util/* subtree would be package-internal, regardless of pub markers further down.

A single non-pub link in the chain seals off everything below it from outside consumers.

What pub exposes

  • pub struct Foo — the struct type is importable.
  • pub interface I — the interface is importable.
  • pub function f — the function is importable.
  • pub type T = ... — the alias is importable.
  • pub var X — the module-level variable is importable (and writable; see 06-variables.html).

For structs, each field has independent visibility. A pub struct with all-private fields can be returned and held but not constructed or destructured outside its module.

extend blocks have no pub modifier themselves. They are anonymous and module-bound: an extend block activates in any module that imports its defining module (in any of the three import forms). The orphan rule (10.9) constrains an extend T: I block to live in either T's or I's defining module, so the set of possible extension sources for any value is small and grep-able.

No finer-grained visibility

There is no pub(crate), pub(super), pub(in path), etc. The chain of pub mod declarations and per-item pub is the entire lattice:

  • "Visible within this file": leave the item private.
  • "Visible to my package only": pub the item; declare its containing mod without pub somewhere along the chain.
  • "Visible to external consumers": pub the item; pub mod the whole chain.

If two sibling files need to share internals without exposing them globally, place them under a common parent that's declared mod (not pub mod). Items marked pub are then reachable from siblings under the same parent but invisible outside the package.

17.6 No top-level runtime

There is no module-load runtime — modules do not execute code on import. Specifically:

  • Module-level var initializers must be compile-time constants (see 06-variables.html). Their values are computed at compile time and embedded into static storage.
  • There is no equivalent of a JavaScript "module body" or a Python module-level execution.
  • There is no implicit main runner per module.

Practical consequence: import order, transitively, does not matter at runtime. The compiler builds the symbol graph; the linker fills in addresses; the program starts at main.

17.7 Circular imports

Circular imports are allowed. Because there is no module-level runtime code, there is no possibility of "using a module before its body has run". The compiler resolves type and function references regardless of cycle:

// module a
import { B } from "self:b"
pub struct A { b: B }

// module b
import { A } from "self:a"
pub struct B { a: A }

Two cautions:

  • A cyclic type definition like pub struct A { b: B } and pub struct B { a: A } is recursive through references; the struct fields are pointers to heap objects, so the recursion is well-founded (each value's size is finite).
  • The compiler must still solve generic constraints transitively; pathological generic cycles (e.g. f<T: g<T>>) are caught at compile time.

17.8 Built-in modules — core: and std:

Two reserved prefixes identify modules supplied by the toolchain:

  • core: — the compiler/runtime substrate. It contains language-privileged definitions: desugar targets, runtime-recognized layouts, syntax protocols, FFI substrate, atomic primitive contracts, and compiler/macro APIs. No core: module is implicitly in scope: even List (from core:collections) must be imported by name. The one thing the toolchain supplies without an import is the desugaring of built-in syntax — see the prelude rule below.
  • std: — the official toolchain library surface. A std: module may be portable, target-backed, or mixed; what makes it std: is that it is ordinary library API rather than compiler substrate. Must be explicitly imported.

The name distinction reflects authority, not portability. If the compiler or runtime must recognize a definition specially, it belongs under core:. If users could implement the same shape as an ordinary library, it belongs under std: even when it can run on a freestanding target.

Only built-in syntax (via core:prelude's desugaring) is implicitly available; every name — List, Map, panic, … — needs an explicit import.

You cannot:

  • Create a module whose path starts with core: or std:.
  • Shadow or re-export names from these prefixes.

The prelude rule — syntax is free, names are imported

There is no auto-imported set of names. The single rule is:

Built-in syntax never needs an import; every named symbol does. Writing a + b needs no import — but writing the name List does.
  • Free (no import): literals ([1, 2] list literals, map literals, number and string literals, string interpolation), operators (+, ==, [], …), for, ?, await. The compiler resolves these through language-known core substrate and stored toolchain definitions without placing any names in scope.
  • Requires import: every name you actually spell out — List, Map, panic, Clone, ToStr — and every named interface/type you use in bounds, signatures, or calls. Operator protocol labels such as Add are not exported from core:prelude today; user operator overloading is driven by visible extend methods such as add, eq, or lt.

So core:prelude is best understood as a desugar-resolution table, not a bag of in-scope names. Nothing it contains is implicitly visible by name.

core:prelude

Defines importable interfaces and primitives that built-in syntax depends on. They are resolved through stored toolchain definitions for syntax; to refer to an exported item by name, import it from core:prelude.

  • Core contracts used by operators and containers — Eq, Ord, and Hash. Ord is the boolean comparison contract; the memory-ordering Ordering value lives separately in core:sync/atomic. Arithmetic and bitwise operator labels such as Add are compiler-recognized method protocols today, not importable core:prelude exports.
  • Iterator protocol — Iterator<T>, Item<T>, Done.
  • Future protocol — Future<T>, Ready<T>, Pending, Context.
  • Error propagation — Try<O, R>, FromResidual<R>.
  • Lifecycle — Clone, Drop.
  • Stringification — ToStr (used by string interpolation; see 01-lexical.md §1.9 and 15-operators.md §15.10).
  • FFI — ReprC and ABI layout rules are compiler substrate. Named boundary helpers such as Foreign, CString, CStr, Buffer, C-width aliases, c_void, and c_va_list live in core:ffi and are explicitly imported. See 19-ffi.html.
  • Panic — panic(msg: str), panic_with(value: T). Like any name, these are imported: import { panic } from "core:prelude".

Two things remain reachable without an import because they are not names you bring into scope: methods on primitive str (str is heap-allocated and its methods are inherent to the type), and numeric helper namespaces (i32.wrapping_add etc.) — numeric primitives are keywords, so their static methods come along for free.

core:collections — compiler-backed containers

The general-purpose heap container types live here because literals, iteration, indexing, and runtime layout make them part of the language substrate. They are ordinary names: import what you use.

import { List, Map, Set } from "core:collections"

var xs = [1, 2, 3]                 // list literal — no import needed for the literal…
var ys: List<i64> = List.new()    // …but naming the type List does
  • List<T> — growable list.
  • Map<K, V> — hash container with a deterministic toolchain hasher today; public hasher customization belongs in std:hash.
  • Set<T: Eq> — unique-list set today; hash-backed storage is planned with generic map-key support.
The default hasher is deterministic Map/Set default to a fixed-seed hasher — fast and portable, but not HashDoS-resistant. If a map ingests untrusted, attacker-chosen keys (e.g. request data on a server), use explicit keyed hasher values from 24 §11. Direct keyed map/set construction remains planned.

core:ffi — explicit-import FFI module

The FFI surface beyond ReprC and Buffer lives in core:ffi. It is core:-tier because the compiler and runtime must recognize ABI, pinning, callback, and foreign-allocation contracts, but it is not auto-imported:

import {
  c_int, c_uint, c_long, c_ulong, c_size_t, c_void, c_va_list,
  Foreign, CStr, CString, Buffer,
} from "core:ffi"

Pinning helpers, callback wrapper types, and foreign-thread attach/detach helpers are planned in 19-ffi.html, but they are not catalog exports until their runtime/compiler contracts are implemented.

core:async — explicit-import async syntax protocols

Future, Ready, Pending, Context, and AsyncIterator are compiler-recognized async shapes. They are exported from core:async because await, async, and for await lower through these contracts. Runtime helpers such as sleep, timeout, and executor scheduling remain in std:async.

import { Future, Ready, Pending, Context, AsyncIterator } from "core:async"

core:sync/atomic — explicit-import atomic primitive contracts

Ordering and its Relaxed, Acquire, Release, AcqRel, and SeqCst variants live in core:sync/atomic because atomic operations require compiler/runtime primitive semantics. The current implemented slice includes the value contract, constructor helpers, and runtime-backed atomic handles for signed/unsigned integers, booleans, and typed raw pointers.

import { Ordering, SeqCst, ordering_seq_cst } from "core:sync/atomic"

17.9 Shadowing rules at import

  • A local definition silently shadows an import. If a module both imports Foo and defines its own Foo, the local one wins in that module.
  • Importing the same local name from multiple imports is an error. You must alias one or both.
  • A namespace name (the as Name of an import "..." as Name) collides with any other binding of the same name in the file. Alias it with a different Name to resolve.

17.10 Re-exports — pub import

pub mod exposes an entire submodule. To selectively re-export from one module under another's public API, use pub import. All three import forms work with a pub prefix:

pub import lifts individual names without exposing their containing submodule.
// src/lib.otter
mod internals                                            // private — pkg consumers can't reach internals/*
pub import { Logger } from "self:internals/log"          // re-export an individual name
pub import { Db, open } from "self:internals/db"

pub function version(): str { "1.2.3" }

Syntax and forms parallel import exactly, with pub prepended:

pub import "pkg:iter_ext"                            // re-export extension activation
pub import "pkg:json" as Json                        // re-export as namespace
pub import { Foo, bar }    from "self:util/helpers"  // re-export names
pub import { Foo as Bar }  from "self:util/helpers"  // re-export with alias

The re-exported names — and the namespace, and the ambient extensions — appear in the re-exporting module's pub set. Importers of the re-exporting module see them as if they were defined locally.

Semantics

  • pub import simultaneously imports into the current module (so the current module can use the names / namespace) and re-exports them as part of this module's public API.
  • For the re-export to be reachable from an external consumer, the declaring module itself must be on a pub mod chain — pub import doesn't bypass module visibility.
  • Re-exporting a name does not produce a new type, struct, or function — it's still the same definition, just reachable under a new path.
  • Collision rules (17.9) apply: a pub imported name that collides with a local definition or another import is an error; alias one or both with as.
  • The bare form pub import "<path>" makes the target module's extensions ambient for any consumer of this module too — useful for "umbrella" packages that pull in several extension packages and re-export their methods.

What this lets you do

  • Curate a flat public API at lib.otter while keeping the internal directory tree as deep as you want.
  • Move implementation files around without changing the public API spelling — consumers always see the lib.otter paths.
  • Build an umbrella package that re-exports several extension crates: consumers do one import "pkg:fancy-iters" and pick up all the re-exported extensions transitively.
  • Mix pub mod-style "expose the whole submodule" with pub import-style "lift individual names" without conflict.

Specific names from a moduleimport { Foo, bar } from "pkg:m"
Umbrella package that re-exports extensionspub import "pkg:dep" in lib.otter
Style guidance (lint, not error) Prefer the self: root form for cross-cutting modules (logging, types, constants) — the path stays meaningful in error messages and grep results. Prefer the self: relative form for tightly-coupled siblings or children — the path stays valid if the subtree moves. Use file: only for genuine non-module data, never for code that could be a module.

17.12 Compilation units

A module is a single source file. Multiple files form a project; the build tool composes them into one program (or library). Modules are compiled independently and combined.

pub and the orphan rule (see 10-interfaces.html) together ensure that the import graph never produces ambiguous or conflicting type/interface configurations.

17.13 Run modes — project context vs direct execution

Which schemes an import may use depends on whether the compilation has project context: a manifest, a dependency set, and a module tree rooted at a declared entry. Two things are orthogonal:

  • Invocation form — are you running the project's entry, or a file by path?
  • Project context — is there a project the file belongs to? A file run by path may still have it (if it sits in a project's module tree) or not (a loose script).

You can have either, both, or neither.

The commands

  • otter_fusion run (optionally --bin <name>) — builds and runs the project's declared entry, Rust-style. Always project context. All schemes available; file: is allowlist-gated.
  • otter_fusion run <path>.otter — direct mode. The toolchain walks up for a manifest and checks whether the file is reachable in that project's module tree:
    • reachable → it also gains project context: self: and pkg: work; file: is allowlist-gated.
    • not reachable / no project → no project context: self: and pkg: are hard errors; file: is unrestricted.
  • otter_fusion exec <path>.otter — force standalone execution: ignore any surrounding project even if one exists. Always "no project context". The escape hatch for treating a file as a throwaway script.

An entry run in direct mode must still define function main(). mod declarations are a project-only feature — they build the explicit module tree, so a file run with no project context may not declare mod. A standalone script is a single entry plus whatever it pulls in via file:.

17.14 Reserved & deferred

The following are intentionally not part of the language today, but the syntax space is reserved so they can be added without a breaking change.

  • Binary blob includes (*+blob:) — embedding a file's bytes as a compile-time constant (à la include_bytes!). Deferred — design pending. When added it must define what it binds (a compile-time Buffer / [u8] constant) and a single-value binding form, since import today binds names, namespaces, and extensions, not values.
  • pkg: in direct mode — today a hard error: direct execution has no manifest, so there is nothing to resolve pkg: against (see 17.13). The dependency, lockfile, and registry model itself is fully specified in 23 §7 — what direct mode lacks is the per-project manifest + lockfile. A future user-global resolver (resolving pkg:<name> against the user-level store / default registry without a project) could lift the restriction; the import spelling stays identical — only the resolver gains a fallback location.
  • URL imports — reserved as a distinct scheme family: url:, http:, https:. Kept separate from pkg: on purpose: pkg: means "a named dependency the resolver maps to a location," whereas a URL import carries its own integrity / lockfile / caching / security model (you are fetching arbitrary remote code) that is cleaner isolated behind its own prefix. This is the only place a URL belongs in source: a registry-hosted package is still imported as pkg:foo/bar with its location living in the manifest + lockfile (23 §7) — there is deliberately no pkg+https://… import form. Reserved only — not implemented.
