16. Memory Model

Tracing GC (Immix mark-region, optionally generational via StickyImmix), driven by precise stack maps emitted by Cranelift. Two disjoint heaps — managed and foreign. Drop is best-effort, asynchronous, and not guaranteed to run — release resources explicitly.

1. The two heaps

Distinct address ranges. A runtime address-range check classifies a pointer as managed or foreign; the GC ignores foreign pointers entirely.

2. Value vs reference semantics

Value (primitives)

Stored inline (stack, struct fields, registers). Assignment copies the value.

i8..i64, u8..u64, f32, f64, bool, char, null, usize, isize.

Reference (the rest)

The variable holds a managed-heap pointer. Assignment copies the pointer; both bindings observe the same object. Mutation through one binding is visible through every other binding holding the same pointer. The GC keeps the object alive for as long as any reachable binding references it.

str, List<T>, Map<K, V>, structs, interface objects, function values that capture state, boxed tuples.

To get an independent copy, call .clone() — see 15-operators §Clone.

3. Object layout

Every managed-heap object has the same two-word header. The pointer held by a variable points to the start of the object fields; the header lives at negative offsets — so field access does not need to skip the header.

Exact sizes are implementation-defined; treat the layout as conceptual. extern struct types have no object header.

An interface reference is still a fat pointer when the required vtable isn't the object's primary one (multi-interface bridging); the single-interface case can collapse to a thin pointer. Primitive boxes for dynamic

Primitives (i32, f64, bool, char, null, …) carry no header on their own — they live inline. When a primitive is widened to dynamic (see 12-type-logic §5), the runtime wraps the value in a heap-allocated box with the standard two-word object header. The type pointer identifies the boxed primitive (i32-box, f64-box, …); the payload sits immediately after, just like any struct field.

Narrowing back via as i32 reads the type pointer to confirm and returns the payload. Boxes themselves participate in tracing like any other managed object. Whether the runtime interns common boxes (small integers, common chars) is implementation-defined; box identity is not exposed to the language.

4. Tracing GC — Immix & StickyImmix

The runtime uses MMTk with the Immix plan (or StickyImmix for generational behavior — same memory layout, two flips in configuration). Immix is a mark-region collector with opportunistic evacuation: the heap is carved into 32 KiB blocks of 128-byte lines; objects are bump-allocated into recyclable holes; fragmented blocks are evacuated lazily.

Mark-region with opportunistic evacuation. Compaction happens only where it pays — no dedicated copying nursery is required.

StickyImmix — generational without a separate nursery

StickyImmix flips one bit per block to remember "this object survived the last collection." Young (unmarked) objects in old (sticky) blocks are reclaimed by a fast nursery-only pass; full collections happen less often. No nursery copying, no separate space — same blocks, two passes of the same collector. This is the default plan for production builds.

Why Immix Mark-region beats mark-sweep on fragmentation, beats semi-space on memory overhead, and beats classical generational copying on simplicity. Production-tested in V8, Julia, and OpenJDK research builds. We get a battle-tested collector by integrating MMTk rather than rolling our own.

6. Safepoints & stack maps

The collector needs to identify every managed pointer on every thread's stack. Instead of scanning conservatively (false-retention prone, hostile to moving) the compiler emits precise stack maps at each safepoint: a per-call-site descriptor of which SSA values and stack slots hold managed pointers.

Cranelift's user_stack_maps mode keeps managed pointers precisely tracked; the runtime never scans the stack blindly.
Why precise, not conservative Conservative scanning treats every word-sized stack value as a potential pointer. That defeats moving collection (you can't rewrite pointers you only suspect exist) and causes false retention. Precise stack maps cost a small per-call-site metadata table and a tiny IR annotation — paid back many times over by tighter heap usage and the ability to evacuate.

7. Write barriers

When a field of a managed object is overwritten with another managed pointer, the compiler emits a write barrier — a short code sequence that informs the collector. The barrier flavor depends on the active plan:

  • StickyImmix needs a remembered-set barrier: old-space writes that point to young-space objects record the slot, so the next nursery collection sees the old-to-young edge as a root.
  • Concurrent marking needs a SATB (snapshot-at-the-beginning) or incremental-update barrier so the collector doesn't miss objects that became reachable mid-cycle.
Cost in practice A typical write barrier is 3–5 inlined instructions on the hot path (a card-table store or a remembered-set buffer push). Cranelift inserts it at every store of an r64 into a heap location; stores into stack slots and primitive stores are unbarriered.

8. Drop semantics

For ordinary managed objects, Drop is best-effort: when the collector determines an object is unreachable, its descriptor's drop slot (if any) is enqueued to the finalizer queue. A dedicated finalizer thread pops the queue and runs each drop in turn.

Generic types implement Drop too extend<T> Box<T>: Drop gives every instantiation a finalizer. Because each monomorphization compiles its own drop body (the field layout and any T-specific calls differ per T), the drop slot is keyed per instantiation, not per generic type — Box<i64> and Box<str> run distinct drop glue. A generic @RefCounted type keeps the same deterministic, scope-bound release as a non-generic one (§8.1).
Release resources explicitly when you need deterministic destruction — Drop is asynchronous and not guaranteed.

Don't rely on Drop for correctness Programs that need deterministic finalization (file flushing, transaction commit, lock release) must release resources explicitly by calling the relevant method (file.close(), lock.release(), tx.commit()) before the binding goes out of scope. There is no general language-level scope-exit hook — like JavaScript, Python without with, or Java without try-with-resources, cleanup of ordinary managed objects is a manual responsibility.
Exception — runtime endpoint handles release deterministically A small set of runtime handle types carry a stronger guarantee than best-effort Drop: channel endpoints (Sender<T> / Receiver<T>, see 20-concurrency §2). Each channel keeps a reference count of its live senders and receivers; the compiler emits a deterministic, scope-bound release of an endpoint when the worker that owns it returns (a Sender captured into a Thread.spawn worker is released the instant that worker finishes, and Sender.clone() registers another producer). When the last sender is released the channel closes immediately — without waiting for a collection — so a drained recv() resolves to ChannelClosed and a for x in rx loop terminates. This is a runtime/library mechanism layered on top of the collector (the GC still reclaims the underlying queue once both ends are unreachable); it does not introduce a general user-facing destructor. The opt-in @RefCounted object kind (§8.1) generalizes this deterministic-drop facility to user types, with the tracing GC as the cycle-collector backstop.

8.1 Deterministic reference counting — @RefCounted

A struct may opt in to deterministic, atomic reference counting with the @RefCounted decorator. This generalizes the channel-endpoint mechanism above into a real language feature: any annotated type gets a deterministic Drop the instant its last strong reference goes away — no waiting for a collection — while the tracing GC is retained purely as the cycle-collector backstop (reference counting alone leaks cycles; the collector reclaims them, Python-style).

@RefCounted
struct Conn { fd: i64 }

extend Conn: Drop {
  function drop(self) { close_fd(self.fd) }   // runs at strong-count 0, synchronously
}

function main() {
  var a: Conn = Conn { fd: open() }   // strong count 1
  var b: Conn = a                     // shared: count 2 (assignment retains)
  use(b)
}                                     // count 2 → 1 → 0: drop(self) runs here, then freed

Drop is optional@RefCounted works with or without a Drop impl: you always get deterministic free at count zero; with a Drop impl you also get deterministic finalization (instead of the GC-timed best-effort drop of ordinary managed objects).
CyclesA reference cycle keeps its members' counts above zero, so reference counting alone never frees it. The tracing GC reclaims the unreachable cycle (running each member's Drop on the finalizer path) — the Python-style backstop.
The determinism boundary Deterministic, synchronous drop is guaranteed for a @RefCounted value held by a local binding (released at end of its function or when re-bound/reassigned) or owned by a field of another struct/tuple (released when that owner is destroyed). A refcounted value that escapes into a GC-managed container or a wider shape — a List/Map/Set element, a Shared<T>, a channel message, a union/dynamic box, or a value captured into a closure — is pinned alive while that holder references it and then reclaimed by the GC backstop (its Drop still runs, but GC-timed, not at the deterministic point). This is always memory-safe: a value is never freed while any holder — counted or GC-traced — still references it.
Placement @RefCounted decorates a plain managed struct only. It is rejected on an extern struct (C-ABI, header-less, unmanaged) and is incompatible with @Transparent (a newtype with no header to host the count). A future iteration may add a Weak<T> companion for breaking cycles without the GC; today the collector is the sole cycle reclaimer.

9. Inline / stack allocation

The compiler may stack-allocate small managed objects when their lifetime is provably bounded by a single frame. Invisible at the language level — observable semantics are always as if the object lived on the managed heap.

Tuples and small structs are the most common candidates. The compiler proves the value does not escape (returned, captured into an escaping closure, sent over a channel, stored in a collection) and replaces the heap allocation with a stack slot. Stack-allocated objects still carry the two-word object header so type identification and GC tracing work uniformly.

10. Type identification

Every managed object's header holds a pointer to its type descriptor: a runtime structure with size, field map (for tracing), drop slot, and the vtable. This is what is/as and interface dispatch consult.

Type descriptors are deduplicated across compilation units. Across separate compilations or dylib boundaries, a runtime registry maps type identity by structure (nominal types by fully-qualified module-and-name; tuple shapes by structural hash). Descriptors themselves live in the immortal space and are never collected.

11. Allocation failure

Managed allocation is infallible (panics on OOM) There is no fallible alloc for managed code. The fast path tries the bump pointer, the slow path requests a fresh block from MMTk, MMTk may trigger a GC, and only if a full collection still cannot satisfy the request does the runtime panic. Foreign allocation via malloc is fallible — returns null to the user. See 19-ffi.

12. Concurrency interactions

  • Each mutator thread has its own thread-local allocation buffer (TLAB) — no contention on the alloc fast path.
  • GC is parallel (multiple collector threads) and may be concurrent (mutators keep running during marking, modulo brief pauses at safepoints). The default plan is parallel marking with short stop-the-world flips.
  • Cross-thread reads/writes of struct fields are not synchronized — use Shared<T> or channels.
  • Write barriers ensure cross-thread heap stores are visible to the collector even when mutators race.
Memory safety vs race-freedom The language guarantees memory safety (no use-after-free) for managed pointers across threads. It does not guarantee race-freedom on object contents — that's on you. See 20-concurrency.

13. Pinning

Pinning a managed object prevents the GC from moving it. It does not prevent reclamation — a pinned object that becomes unreachable is still collected (the runtime will not move it during that collection's evacuation; in-place sweep reclaims it). Reachability is the regular root scan; pinning is purely an immovability declaration.

Prefer @Pinnable for types that are pinned often; reserve dynamic pinning for short transient cases.
Long-term dynamic pins fragment the heap A pinned object in default Immix blocks evacuation of its block. For values you'll retain across many collections (callback registrations, foreign-stored references), prefer @Pinnable on the type — or use a handle (§15) instead.

See 19-ffi §pinning for the surface syntax.

14. Handles — long-lived foreign rooting

When foreign code needs to retain a managed pointer across calls — a GUI library that stores your callback target, a registry of observers, a long-running native task — pinning is the wrong tool. The right tool is a handle: an opaque, integer-sized cookie that:

  • Is a GC root in the runtime's handle table (so the object stays alive).
  • Does not prevent movement (so Immix stays free to compact).
  • Resolves to the current object location through one indirection at deref.
JNI-style global refs, but typed. Cheap to create, free to keep, and movement-friendly.
Pin vs Handle — choosing
  • Pin when the foreign side needs a real pointer to the object's bytes (synchronous call passing a buffer to C, output-parameter writes).
  • Handle when the foreign side stores the reference and calls back later, or when many references are retained — anything where movement-blocking would hurt the heap.
  • Both in a small number of cases: a pinnable type held via a handle, for long-lived foreign storage that also needs a stable address.
Release explicitly Handle.release() must be called when the registration is removed. The handle's Drop impl will release the table slot eventually, but eventually means "whenever the finalizer queue gets to it" — possibly never. Each leaked handle keeps its referent alive forever and consumes a table slot.

15. Summary

  • Tracing GC: MMTk with the Immix plan (StickyImmix for generational).
  • Two-word object header: [type ptr | mark/forwarding]; pointer at the field boundary.
  • Precise stack maps from Cranelift (user_stack_maps); safepoints at calls and loop back-edges.
  • Write barriers inserted at IR-gen for cross-space and concurrent-marking correctness.
  • Allocation spaces: default (Immix), nonmoving (for @Pinnable), immortal, los.
  • Drop is best-effort by default — finalizer queue, no ordering.
  • @RefCounted opts a struct into deterministic, atomic reference counting: Drop runs synchronously at strong-count zero; the GC is the cycle backstop (§8.1).
  • For ordinary managed objects there is no deterministic-drop hook — release resources explicitly.
  • Pinning prevents movement, not reclamation. @Pinnable avoids dynamic pins.
  • Handles for long-lived foreign rooting — movement-friendly alternative to pinning.
  • Managed alloc panics on OOM; foreign alloc returns null. Two heaps; GC ignores foreign pointers.
